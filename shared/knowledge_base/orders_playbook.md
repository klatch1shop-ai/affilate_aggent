# Замовлення NOIRE: що ми вміємо (станом на 13.09.2026)

Довідка по всіх методах, які перевірені на живих даних. Позначка **✅** —
метод викликано й результат перевірено читанням; **⚠️** — є в коді, але
жодного разу не перевірявся.

Детальні довідки: [novaposhta/README.md](novaposhta/README.md),
[api_reference.md](api_reference.md) (Rozetka), `docs/AGENT_RULES.md`.

## Ланцюжок замовлення

```
Rozetka: нове замовлення (1)
  → наявність у SexOpt (база sexopt_products)
  → оплата (payment.payment_status)
  → статус 26 «Обробляється менеджером»
  → статус 2 «Комплектується. Дані підтверджені»
  → [ЗАВТРА] замовлення в постачальника
  → ТТН Нової Пошти (tools/np_create_ttn.py)
  → ТТН у Rozetka + статус 61 «Заплановано передачу перевізникові»
  → наклейка 100×100 у Telegram
```

## 1. Rozetka Seller API

Доступ: `RZ.rz_headers()` в `agents/orders/rozetka_order_agent.py` (токен у `.env`).

| Що робимо | Запит | Де в коді | |
|---|---|---|---|
| Нові замовлення | `GET /orders/search?types=4` і `?status=1/2/26/55/61` | `get_new_orders()` | ✅ |
| Деталі замовлення | `GET /orders/{id}?expand=status_available,payment,delivery` | `get_order_details()` | ✅ |
| Які статуси можна поставити зараз | той самий `GET` → `status_available[].child_id` | `_status_available()` | ✅ |
| 1 → 26 «обробляється менеджером» | `PATCH /orders/{id}` `{"status": 26, "comment": "Наявність перевірено"}` | `move_to_processing()` | ✅ |
| 26 → 2 підтвердити | `PATCH /orders/{id}` `{"status": 2, "comment": "Підтверджено"}` | `confirm_order()` | ✅ |
| ТТН + статус 61 | `PATCH /orders/{id}` `{"status": 61, "ttn": "<ТТН>"}` | `np_create_ttn.rozetka_ttn()` | ✅ 13.09, #905931436 |
| Назви всіх статусів (86) | `GET /order-statuses/search?page=N` | — | ✅ |
| Скасувати | `PATCH /orders/{id}` `{"status": 6, "comment": ...}` | `cancel_order()` | лише Carvol і лише коли доведено, що товару немає |
| Додати ТТН (старий спосіб) | `POST /orders/add-ttn` `{order_id, ttn, delivery_service_id: 1}` | `set_ttn()` | ⚠️ жодного разу не викликали |

**Поля замовлення, які ми використовуємо:**

| Поле | Значення |
|---|---|
| `status` | поточний статус |
| `amount` | сума замовлення (іде в ТТН як оголошена вартість) |
| `payment_type`, `payment.payment_status.name` | `"paid"` = оплачено |
| `purchases[].item.article`, `quantity` | артикул (SKU) і кількість |
| `delivery.delivery_service_id` | `5` = Нова Пошта |
| `delivery.ref_id` | **Ref відділення НП**, одразу придатний для ТТН |
| `delivery.place_number` | номер відділення (звіряємо з НП) |
| `delivery.recipient_first_name / last_name / second_name`, `recipient_phone` | одержувач |
| `delivery.declaration_number` | ТТН. Лежить тут, а **не** в корені замовлення (`_ttn_of()`) |

**Статуси, з якими ми працюємо:**

| id | Назва | Хто ставить |
|---|---|---|
| 1 | Нове замовлення | Rozetka |
| 26 | Обробляється менеджером | агент (після перевірки наявності) |
| 55 | Очікує отримання оплати | агент |
| 2 | Комплектується. Дані підтверджені | агент (після оплати) |
| 61 | Заплановано передачу перевізникові | `np_create_ttn.py` (разом із ТТН) |
| 3 | Передано до служби доставки | — |
| 4 / 5 | Доставляється / Очікує в пункті самовивозу | Rozetka |
| 6, 40, 49 | Скасування, «клієнт передумав», «небезпечний» | агенту **заборонено** (`FORBIDDEN_STATUSES`) |

**Правила:**
- Зі статусу 1 API пропонує лише 26. Будь-який перехід беремо тільки зі `status_available`.
- Після кожного запису перевіряємо результат повторним читанням.

`{"apiKey", "modelName", "calledMethod", "methodProperties"}`. Ключ у `.env` (`NP_API_KEY`).

| Модель.метод | Для чого | |
|---|---|---|
| `Address.getCities` | Ref міста (знайшли Дніпро) | ✅ |
| `Address.getWarehouses` | відділення за `Ref` або `CityRef` + `WarehouseId` | ✅ |
| `Counterparty.getCounterparties` `{CounterpartyProperty: "Sender"}` | наш відправник | ✅ |
| `Counterparty.getCounterpartyContactPersons` | контактна особа й телефон відправника | ✅ |
| `Counterparty.save` `{PrivatePerson, Recipient, ПІБ, Phone}` | одержувач → `Ref` + `ContactPerson.data[0].Ref` | ✅ |
| `Counterparty.getCounterpartyOptions` | прапорці акаунта (контроль оплати тощо) | ✅ читання |
| `InternetDocument.getDocumentPrice` | вартість доставки без створення ТТН | ✅ |
| `InternetDocument.getDocumentDeliveryDate` | дата доставки | ✅ |
| `InternetDocument.save` | **створити ТТН** → `IntDocNumber`, `Ref` | ✅ |
| `InternetDocument.update` | змінити ТТН (з `Ref`), **лише до друку** | ✅ |
| `InternetDocument.delete` `{DocumentRefs}` | видалити ТТН (до сканування) | ✅ |
| `InternetDocument.getDocumentList` | усі наші ТТН за період, усі поля | ✅ |
| `TrackingDocument.getStatusDocuments` | статус посилки; з `Phone` відправника дає розширені поля | ✅ |
| Друк наклейки 100×100 | `https://my.novaposhta.ua/orders/printMarking100x100/orders[]/{Ref}/type/pdf/apiKey/{key}` | ✅ |
| Друк накладної | `.../orders/printDocument/orders[]/{Ref}/type/pdf/apiKey/{key}` | — |

**Наша стандартна ТТН (вказівки власника 13.09):**

| Поле | Значення |
|---|---|
| Відправник | Дніпро, відділення №1 (`SENDER_CITY`, `SENDER_WAREHOUSE` у скрипті) |
| `PayerType` / `PaymentMethod` | `Recipient` / `Cash`: доставку оплачує одержувач |
| `CargoType`, `Weight`, `SeatsAmount` | `Parcel`, `2`, `1` («посилка до 2 кг») |
| `OptionsSeat` | коробка 30×20×10 см, як у ручних ТТН власника; для поштомата обов'язково |
| `Cost` | оголошена вартість = сума замовлення |
| `Description` | «Косметика», нейтрально (у ручних ТТН власник пише назву товару — не вирішено) |
| `InfoRegClientBarcodes` | номер замовлення Rozetka |
| `ServiceType` | `WarehouseWarehouse` |
| Післяплата | оплачено → немає; оплата при отриманні → `BackwardDeliveryData` на суму замовлення |

**Пастки, які ми знайшли:**
- Порожній `data` при `success: true` буває тимчасово. Треба повторити через кілька секунд (`np()` робить це сам).
- **Після друку наклейки ТТН через API не змінити**: «Document is already printed».
- Післяплата на карту: поле `BackwardDeliveryData[].PaymentCard`. Для нашого ключа НП повертає **20000201794** «тимчасово заблокована». Поки що ТТН створюється без післяплати, а в Telegram іде «додайте післяплату N грн». Після реєстрації ФОП і зміни ключа треба перевірити знову.
- `Payment.getCards` відкритий лише для застосунку НП.
- Тип точки видачі: `DeliveryTo` = `Branch` (відділення), `Postomat` (поштомат), `Store` (пункт приймання-видачі).
- Тестові ТТН створюємо на власника і одразу видаляємо через `delete`.

**Перевірки `np_create_ttn.py` перед створенням ТТН.** Скрипт зупиняється, якщо:
- доставка не Новою Поштою;
- у замовленні вже є ТТН;
- тип оплати невідомий;
- відділення не знайдене або його номер не збігається з Rozetka;
- немає імені, прізвища чи телефону одержувача.

## 5. Правила, яких ми навчились

1. **Наявність має три стани.** «Не змогли перевірити» ≠ «немає». Без доказу нічого не скасовуємо.
2. **Після кожного запису перевіряємо результат читанням.** Відповідь `success` ще не доказ.
3. **Реальні дії спершу пробуємо на тесті.** Тестову ТТН створюємо на власника і видаляємо.
4. Ключі й номер картки зберігаються **лише в `.env`**. Персональні дані клієнтів у git не потрапляють: `shared/feeds/orders/` у `.gitignore`.
5. Carvol лише читаємо, нічого там не змінюємо.
6. Сервер автоматично комітить нові файли. Тому копії `.env` зберігаємо лише поза репозиторієм (`/home/tek/env_backups`).

- `.env`: `SEXOPT_URL`, `SEXOPT_LOGIN`, `SEXOPT_PASSWORD`, вхід у кабінет постачальника;

- Як оформлюється замовлення: форма в кабінеті, API, email чи месенджер?
