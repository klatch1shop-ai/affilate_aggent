# Матриця команд бота-помічника і план розробки

**Дата:** 19.09.2026. **Завдання власника:** «розробляти матрицю команд, які потім будем на
голосові переробляти… покрити API-функції, далі сценарії типу створення накладних, відправка
повідомлень постачальника, зміни, перевірки».
**Джерела:** офіційна документація Rozetka Seller API (`shared/knowledge_base/rozetka/apidoc/`,
356 методів у 41 групі), наші інструменти в `tools/` і `agents/`, модулі TASK-01…08.

## 1. Концепція: один шар команд, голос — лише вхід

```
текст ─┐
       ├─► розбір наміру (intents) ─► параметри ─► перевірка ризику ─► виконавець ─► відповідь
голос ─┘   (Whisper → текст)                        (§2)               (адаптер/сценарій)
```

- **Кожна дія існує один раз** — як команда з наміром, параметрами й рівнем ризику. Голос не
  отримує окремої логіки: це розпізнавання мови (Groq Whisper — ключ уже є у скіла `watch`)
  перед тим самим розбором. Тому спершу будуємо **текстові** команди, голос додається в кінці.
- **Відповідь завжди текстом** (і, за бажання, голосом згодом).
- **Сценарій** — це послідовність команд із перевірками між кроками (напр. «оформити
  відправку»: наявність → ТТН → ТТН у Rozetka → повідомлення). Кожен крок — окрема
  команда з матриці, тож сценарій не має власних прихованих дій.

## 2. Рівні ризику — головне правило безпеки

| Рівень | Що це | Приклади | Як виконується |
|---|---|---|---|
| **R0 читання** | нічого не змінює | нові замовлення, де посилка, баланс, товари на модерації | одразу |
| **R1 чернетка** | готує, але не відправляє | текст відповіді покупцю (Gemini), лист постачальнику, розрахунок ціни | одразу, результат — «чернетка» |
| **R2 зворотний запис** | змінює, але можна відкотити | позначити чат важливим, додати ТТН у замовлення Rozetka, «в обробці» | показати **що саме** зміниться → кнопка **✅ Виконати / ❌ Скасувати** |
| **R3 незворотне / люди / гроші** | не відкотити або бачить інша людина | створити ТТН НП, надіслати покупцю, лист постачальнику, скасувати замовлення, повернення коштів | як R2 **+** повтор усіх параметрів **+** режим `off/test/live` для кожної команди **+** журнал |

**Голосом R2/R3 ніколи не виконуються одразу** — голос лише готує дію, підтвердження тільки
кнопкою (помилка розпізнавання не має відправити ТТН на чужу адресу).

**Заборонено боту взагалі** (правила власника): оплата постачальнику; ціна нижче порогу
(роздрібна ціна постачальника); зміна змісту фідів Rozetka після модерації (лише ціна й
наявність); будь-які зміни по Carvol; скасування замовлення без доказу відсутності товару.

## 4. Сценарії (багатокрокові), які з'являться після фаз A–C

1. **«Оформити відправку замовлення N»**: картка замовлення → наявність у постачальника →
   (R1) чернетка ТТН з параметрами → ✅ → (R3) ТТН НП → (R2) ТТН у Rozetka → звіт.
2. **«Замовити в постачальника по N»**: (R1) лист/Excel постачальнику → ✅ → (R3) відправка →
   запис у звірку 21:00 → звіт увечері, чи прийшла ТТН.
3. **«Повернення по N»**: деталі заявки + листування → рішення власника → (R3) статус →
   (R2) ТТН повернення.
4. **«Відповісти покупцю»**: картка → Gemini-чернетка з урахуванням товару/замовлення →
   правка власником → ✅ → (R3) надсилання. (Автовідповіді — окрема розмова з власником.)
5. **«Ранкова перевірка»**: звіт 9:00 + кнопки «показати замовлення без ТТН / чати / модерацію».

## 5. План розробки (кожна фаза — завдання Codex з тестами наперед + підключення Claude)

| Фаза | Що | Завдання Codex | Ризик | Оцінка |
|---|---|---|---|---|
| **A1** | Розширений розбір намірів: усі R0-команди з §3 (≈20 нових намірів, періоди, статуси, номери повернень), таблиця прикладів фраз як тести | TASK-09 `intents v2` | R0 | 1 завдання |
| **A2** | Адаптери читання: лічильники, повернення, відгуки, баланс/рахунки, модерація по джерелу, ТТН без руху | TASK-10 `integrations v2` | R0 | 1–2 завдання |
| **A3** | Відкриті давні чати карткою, розумні нагадування, окремі курсори типів чатів | TASK-11 `inbox v2` | R0 | 1 завдання |
| **B** | **Механізм підтвердження**: «відкладена дія» (що, з якими параметрами, ризик, хто, коли), кнопки ✅/❌, строк дії, журнал, режими `off/test/live` на команду | TASK-12 `confirm` | — | 1 завдання, **ключове перед будь-яким записом** |
| **C** | R2-команди: ТТН у Rozetka, «в обробці», продовжити резерв, позначки чатів | TASK-13 | R2 | 1 завдання |
| **D** | R3-сценарії: ТТН НП (через наш `np_create_ttn`), лист постачальнику, відповідь покупцю (Gemini-чернетка → ✅), повернення | TASK-14…16 | R3 | 3 завдання, кожне — з дозволу власника на `live` |
| **E** | Голос: голосове повідомлення → Groq Whisper → той самий розбір; голос ніколи не підтверджує R2/R3 | TASK-17 | — | 1 завдання |

Порядок: **A1 → A2 → A3 → B → C → D → E.** Фаза B — межа: до неї бот лише читає й готує
чернетки.

## 6. Потрібно від власника

1. Підтвердити рівні ризику (§2): що саме можна робити одним натиском кнопки, а що — лише
   після повтору параметрів.
2. Звірити значення `user_rating` (рівень викупу) — для команди «викуп покупця».
3. Новий ключ Prom — для команд Prom (зараз 401).
4. Коли дійдемо до D: окремий дозвіл на `live` для кожної R3-команди після пробного прогону в `test`.

## 7. Дослідження: як будують такі канали керування (20.09.2026)

Що беремо з практики 2025–2026 і чому:

| Тренд | Що це | Як у нас |
|---|---|---|
| **Гібридний розбір** | правила першими (швидко, дешево, передбачувано), LLM — лише коли правила не впевнені; результат LLM проходить ті самі перевірки. Дослідження показують: чистий LLM-розбір повільніший і часом обирає не ту функцію; гібрид зберігає точність LLM при швидкості правил | TASK-14: Gemini як запасний розбір для `unknown` і заперечень |
| **Людина в контурі (human-in-the-loop)** | руйнівні й дорогі дії не виконуються самі: стан зберігається як «очікує підтвердження», людина підтверджує в Telegram, виконання відновлюється | TASK-13: pending-дії, строк дії, журнал, ідемпотентність |
| **Шарова безпека** | жодна модель не усуває «хибних виконань» повністю, тому права й обмеження перевіряються **незалежно від LLM** між рішенням і дією | рівні R0–R3 у каталозі; LLM і голос лише створюють pending-дію, підтвердження — кнопкою |
| **Запис вимкнено за замовчуванням** | команди запису потребують явного `confirm`, режими off/test/live | режими на кожну команду в TASK-13 |
| **Проактивні події** | бот сам повідомляє про важливе: скарги, відгуки, нові замовлення, низькі залишки, падіння продажів | ранковий звіт + картки чатів; далі — відгуки, повернення, «товар закінчився» |
| **Один шар інструментів для бота й агентів (MCP)** | ті самі команди доступні і людині в Telegram, і ШІ-агентам як інструменти | каталог команд → згодом MCP-сервер (у `shared/mcp_servers/` вже є заготовки) |
| **Рутини з постійних інструкцій** | «щодня о 18:00 покажи замовлення без ТТН» стає розкладом | після TASK-13: команда «нагадуй щодня …» |
| **Голос як вхід, не як логіка** | розпізнавання мови → той самий розбір | TASK-17: Groq Whisper → текст → правила/LLM |

Джерела: human-in-the-loop через Telegram зі збереженням стану (github.com/dhakad22klx/agent-space#26);
гібридні мовні інтерфейси (ACM VRST 2025, doi 10.1145/3756884.3766015); безпека голосових
команд з LLM (arXiv 2609.19630); шлюзи запису з явним confirm (github.com/marco-ncode/voice-agent#5);
MCP для комерції (Microsoft Dynamics 365 Commerce MCP, 29.06.2026).
