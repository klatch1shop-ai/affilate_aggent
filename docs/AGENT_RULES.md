# Правила розробки агентів — ОБОВ'ЯЗКОВО ЧИТАТИ ПЕРЕД БУДЬ-ЯКИМИ ЗМІНАМИ

## 1. ЗАБОРОНЕНО без явного дозволу користувача
- Змінювати будь-який існуючий агент (rozetka_order_agent.py, epicentr_order_agent.py, tg_dispatcher/main.py)
- Змінювати crontab на сервері
- Перезапускати systemd сервіси (rozetka-order-agent, epicentr-order-agent, tg-dispatcher, feed-server)
- Змінювати .env файл
- Видаляти або перезаписувати дані в БД
- Робити git push з незакоміченими змінами

## 2. ОБОВ'ЯЗКОВО перед будь-якою зміною в існуючому коді
- Прочитати файл повністю перед редагуванням
- Зробити резервну копію: cp file.py file.py.bak
- Перевірити синтаксис: python3 -c "import ast; ast.parse(open('file.py').read())"
- Описати ПОВНІСТЮ що змінюється і чому в commit message
- Після зміни перевірити що сервіс все ще працює: systemctl --user status {service}

## 3. ПРАВИЛА git
- Завжди git pull --rebase перед git push
- Якщо є незакомічені зміни — спочатку git stash або git add + git commit
- Ніколи не робити git push --force
- Commit message має містити: що змінено, чому, який файл

## 4. ПРАВИЛА для нових агентів
- Нові агенти створювати в agents/orders/ з назвою {supplier}_order_agent.py
- Нові інструменти створювати в tools/
- Новий сервіс systemd — тільки після тестування і явного дозволу користувача
- Новий cron — тільки після тестування і явного дозволу користувача

## 5. АКТИВНІ СЕРВІСИ — НЕ ЧІПАТИ БЕЗ ДОЗВОЛУ
- rozetka-order-agent — обробляє замовлення Розетки кожні 5 хв
- epicentr-order-agent — обробляє замовлення Єпіцентру кожні 5 хв
- tg-dispatcher — Telegram бот (PDF, команди, голос)
- feed-server — HTTP сервер фідів

## 6. АКТИВНІ CRON — НЕ ЧІПАТИ БЕЗ ДОЗВОЛУ
- 0 8 * * * price_updater.py — оновлення цін Prom
- 0 */4 * * * feed_sync.py — синхронізація Єпіцентр
- 0 * * * * rozetka_github_sync.py — Carvol XML push

## 7. ПОРЯДОК РОБОТИ З АГЕНТОМ
1. Прочитати поточний код повністю
2. Описати що треба змінити і отримати підтвердження
3. Зробити зміну мінімально — тільки те що потрібно
4. Перевірити синтаксис
5. Скопіювати на сервер через scp
6. Перевірити що сервіс запустився
7. Подивитись лог на помилки
8. git commit з детальним описом
9. git push

## 8. ПРАВИЛА ОПИСУ ЗМІН
Кожна зміна в існуючому файлі має містити:
- Що було до змін (старий код)
- Що стало після (новий код)
- Причина зміни
- Який ефект на систему
- Чи потрібен перезапуск сервісу

## 9. ЗАБОРОНЕНІ ПАТЕРНИ
- Ніколи не використовувати > для перезапису існуючих файлів агентів
- Ніколи не робити sed -i без попереднього резервного копіювання
- Ніколи не змінювати логіку обробки замовлень без тестування
- Ніколи не додавати нові залежності (pip install) без перевірки

## 10. ЯКЩО ЩОСЬ ЗЛАМАЛОСЬ
1. НЕ ПАНІКИ — не роби додаткових змін
2. Перевір git log --oneline -5 щоб знайти останній робочий коміт
3. git revert HEAD або git checkout {commit} -- file.py
4. Скопіювати виправлений файл на сервер
5. Перезапустити сервіс
6. Повідомити користувача

## 11. ПРАВИЛА ВИМІРЮВАННЯ І ВИСНОВКІВ

Три правила, виведені 08-09.09.2026 з підтверджених випадків, а не з міркувань.
Кожне має ціну, яку вже заплачено.

### 11.1. Різниця двох підрахунків — це СПИСОК, який треба відкрити,
### а не число, яке можна інтерпретувати

Три випадки за дві доби, усі з одного джерела:

```
5564 − 5386   → «майже 200 карток є в кабінеті, а у фіді немає»
                НАСПРАВДІ: 37 залишкових рядків таблиці + розпродані
5540 − 5386   → «серед них лежать 12 «не відображаються»»
                НАСПРАВДІ: 12 з 12 у фіді присутні, усі 155 — not_available
12 публікацій → «зміни не доходять до Prom, це важливіше за все»
проти 2 змін    НАСПРАВДІ: автоімпорту справді немає, але дрейф цін
                і наявності — 42 картки на добу, не катастрофа
```

**Дія:** перш ніж робити висновок про природу розриву — вивести перелік
елементів різниці й подивитись, що це за товари.

**Поправка 13.09.2026 до третього рядка.** «Автоімпорту немає» було
неповним: `grep` підтвердив лише, що МИ не викликаємо імпорт через API.
Prom сам тягне файл за посиланням («Автоматичне оновлення посилання — раз
на 4 години», скрін власника). Заміряно через API (дати змін + вміст полів):
імпорт 09:09 застосував лише наявність/кількість (6 карток; 4454 рос.
ключів, 207 рос. і 172 укр. назв із фіду 7:40 лишились старими), а нічний
(~22:00–00:00 UTC) — вміст (2611 карток змінили дату без зміни ціни,
кількості й наявності). Висновок «не відбувається» з перевірки «ми не
ініціюємо» — той самий тип помилки, що в 11.8: відсутність нашої дії
прийнято за відсутність дії взагалі.

### 11.2. Жодна знахідка не йде у виправлення без ОКРЕМОГО заміру наслідку

Навіть якщо форма ідеально збігається з вісьмома підтвердженими дефектами.

Ціна: «дефект 9» був виведений із читання коду за знайомим патерном
(тихий дефолт `gender='m'`). Гілка виявилась мертвою — закритою умовою
`and single`. Замір показав, що товари без запису в довіднику мають **більше**
фраз (8.68 проти 8.47). Написане «виправлення» посилалось на неіснуючу
змінну `_RU_CAT_MISS` і внесло б `NameError` у продакшен.

### 11.3. Жодна правка генератора фіду не розгортається без явного прогону

Лінт `ast.parse` плюс реальний запуск, незалежно від очевидності правки.
Саме тривіальність правки з п.11.2 ледь не пропустила неіснуючу змінну.

### 11.4. Вибірка перевіряється на зміщення ДО використання

```
python3 tools/sample_bias_check.py --file skus.txt
```

`prom_id` зростає з часом створення; медіанний перцентиль випадкової вибірки
має лягти біля 50 %. Поріг динамічний: `100/(2·√n)`, спрацювання за 2σ.

Ціна: вибірка перших 600 через `/products/list` дала 34.7 % карток із датою
09-05 замість справжніх 9.3 % — метод іде за `id`, тож перші сторінки це
найдавніші товари. Медіанний перцентиль такої вибірки — 5.4 %, тобто 21.8σ.

**Ніколи не брати послідовний зріз перших N через `/products/list`.**

### 11.5. Позитивний контроль на самому інструменті вимірювання

Прогін на **завідомо поганому** прикладі, не лише на очікуваних.

Ціна: регекс `company_name` мав ліміт `{1,60}`, назви продавців бувають довші
(69 символів). Через це кількість пар на сторінці виходила меншою за 8,
спрацьовувала умова виходу з пагінації, і обхід обривався після першої
сторінки. Усі заміри з «переглянуто 1-7» були недійсні, і виявилось це лише
тоді, коли контрольний запит із відомою відповіддю дав нуль.

### 11.6. Три підвиди одного класу — вимірювач теж помиляється

Файл описував два: генератор помиляється, валідатор мовчить. Є третій, і за
09.09.2026 він дав більше хибних висновків, ніж перші два разом:

```
1  ГЕНЕРАТОР помиляється     _is_adj пропускав відмінкові іменники
2  ВАЛІДАТОР мовчить          head_noun «підтверджував» тип 5 літерами
3  ВИМІРЮВАЧ ПЕРЕБІЛЬШУЄ      детектор рахує артефакти форматування
                              як помилки продукту
```

Приклади третього, усі за одну добу:

```
20.8 % хибних типів   → насправді 4 %. Детектор не розумів «/», дефіса
                        і складних слів: «портупея/збруя», «Мастурбатор-торс»
25.3 % «класичний»    → насправді 12 %. Детектор шукав підтвердження ЛИШЕ
                        в назві, а «Форма: класична конусна» стоїть в
                        окремому полі
0 підтверджених       → артефакт: вимагав, щоб УСІ слова означення
іншим полем             підтвердились ОДНИМ джерелом, а «анальна» в назві,
                        «класична» в характеристиці
```

Четвертий підвид (12.09.2026) — помиляються не наші інструменти, а
**вхідні дані маскуються під правильні**:

```
4  ВХІДНІ ДАНІ МАСКУЮТЬСЯ     текст постачальника виглядає кириличним, а
                              містить латинські двійники: «свечa», «10cм»,
                              «Кііrоо», «Сlassic» — 142 слова у фіді Prom
```

Жодна з перевірок його не ловила: око бачить правильне слово, словник
русизмів і валідатор перевіряють літери, а не абетку, генератор ключів
будує фрази з «зіпсованого» слова (`гуcтая смазка lubrix`). Ловиться лише
порівнянням абеток у межах слова — `tools/homoglyph.py` (`is_mixed`,
`fix_text`), у фіді Prom — `dehomo()` і `brand_twins()` генератора.
Знайдено випадково: після виправлення змінились ключі кількох карток, і
перегляд цих змін показав наступний дефект (тип товару через прийменник).

**Ознака:** детектор дає високу частку помилок і жодного разу не був
перевірений на прикладі, де він мусить сказати «все гаразд».

**Дія:** перш ніж вірити числу детектора — вручну відкрити 10-15 позначених
ним карток. Якщо серед них є хоч одна, де помилки насправді немає, число
завищене, і масштаб завищення треба виміряти, а не вгадати.

### 11.7. Підтвердження не береться з джерела кандидата

Якщо характеристика породила значення — вона ж не може його підтверджувати.
Це замкнене коло, і воно маскує помилку під перевірку.

```
ПРАВИЛЬНО : «класична анальна пробка» з «Тип товару»
            підтверджуємо назвою АБО полем «Форма», АБО «Конструкція»
ХИБНО     : підтверджуємо тим самим «Тип товару»
```

Виміряно 09.09: із 38 карток зі словом «класичний» **20 підтверджуються
незалежним полем** (`Форма: класична конусна`), 18 — нічим. Без розриву кола
всі 38 виглядали б підтвердженими; з перевіркою лише по назві — усі 38
виглядали б хибними. Обидві крайності неправильні.

### 11.8. Запис рішення — не доказ його дії

Рішення, записане в таблицю чи конфіг, могло не дійти до генератора. Існування
запису приймали за доказ, що він працює, — ніхто не перевіряв, чи хоч один
товар через нього проходить.

Ціна (знайдено 13.09.2026): у `prom_category_mapping` для олій (код 9632) два
рядки без правила — 25 «→ Збуджуючі засоби» (впевненість 0.75, 08.08) і 78
«→ Масажні косметичні засоби» (0.9, 09.08, додано саме щоб виправити 25).
`load_mapping` сортував за `id`, тож виграв старший рядок, і виправлення не
діяло **жодного дня** — масажні олії місяць лежали у «Збуджуючих».

Той самий різновид, що й тихий дефолт `gender='m'` (п. 11.2): пріоритет
вирішує **порядок запису**, а не явний критерій. Там гілка виявилась мертвою
без наслідків, тут дефект справжній.

```
ОЗНАКА : кілька рядків/правил претендують на той самий випадок, і хто
         виграє, визначає id, порядок у файлі чи порядок обходу словника
ДІЯ    : після додавання рядка-виправлення перевірити, що він ВИГРАЄ хоч
         для одного реального товару — tools/prom_mapping_audit.py друкує
         рядки, які не виграють ніде («мертві»)
```

## 12. TOPTUL для Розетки — НЕ ОНОВЛЮВАТИ

Рішення власника від 09.09.2026, діє до його прямого скасування.

```
файл    /home/tek/noire-feed/toptul_rozetka.xml
стан    від 01.09.2026 06:36, 5520 офферів
```

**Причина:** Розетка спершу перевіряє фід перед підключенням, зворотного
зв'язку довго немає. Зміна файлу посеред перевірки може її збити або
скинути на початок.

Я пропонував оновити фід перед листом у підтримку — **пропозиція хибна саме
з цієї причини**, власник її відхилив.

**Що перевірено 09.09 і чому оновлення не станеться саме:**
* крону на `toptul_rozetka_generator.py` немає взагалі;
* `publish_github()` у `noire_stock_sync.py` робить `git add <один файл>`
  поіменно, а не `git add -A`. Публікації Prom, Rozetka NOIRE та Єпіцентру
  не зачіпають цей файл навіть при `push --force`.

**Оновлено 11.09.2026:** фід перезібрано після відмови Rozetka (описи), і
вимога діє далі — Rozetka перевіряє саме цю версію. Генератор на сервері
відтоді працює, але **крон для нього не ставиться**: автооновлення посеред
перевірки зіб'є її. Запуск лише вручну.

**Оновлювати лише за прямою вказівкою власника.** Коли підтримка відповість —
оновлення має бути першим кроком, до того як Розетка почне імпорт, інакше
зайдуть залишки багатоденної давнини.
