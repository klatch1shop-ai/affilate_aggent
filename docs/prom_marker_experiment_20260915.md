# Маркер-експеримент: чи шукає Prom за ключовими словами (старт 15.09)

**Дозвіл:** власник, 15.09 (разом з оцінкою чату).
**Навіщо:** на наявних даних чистий тест ключів неможливий. Генератор будує
ключі зі слів назви, тож будь-який запит із ключів частково збігається з
назвою. Це розділений збіг, а за правилом Prom («Облік ключових слів у
пошуку та тегах») такий товар не показується. Усі попередні докази
«ключі не працюють», зокрема 4 браузерні випадки, мали такий дизайн.

## Дизайн

| | Група UA | Група RU |
|---|---|---|
| маркер | «зорвінтал» | «квербаліс» |
| поле | лише `keywords_ua` | лише `keywords` |
| карток | 50 | 50 |

- **100 карток із 38 категорій** (≤4 на категорію). Спершу 20 з 20 категорій (seed 20260915), о 16:35 розширено до 100 (seed 20260916) — власник: «роби на чим більшу кількість, це буде інформативніше». Усі на
  вітрині й у наявності, поза вибіркою заміру видимості й тестами.
  Перелік і prom_id: `data/prom/marker_experiment.json`.
- Маркера **немає** в назві й описі, лише в ключах. Отже, запит із одного
  слова має збіг тільки в полі ключів, і розділеного збігу немає.
- **Негативний контроль до старту:** обидва маркери дають 0 результатів в
  українському і російському пошуку (HTML, 15.09 ~16:20). Перевірку
  браузером з обома блоками видачі — див. журнал.
- Крок `tools/prom_marker_step.py` — останній у `prom_postprocess.py`.
  Перевірено на копії опублікованого фіду: для 20 і для 100 карток — змінено рівно
  стільки карток, 0 порушень, лише потрібне поле.
- Публікація **15.09 о 19:40**, імпорт вмісту — нічний (~01–03 за Києвом).

## Перевірка

- **Щодня** (16, 17, 18.09), браузером, з обома блоками видачі:
  - запити: маркер в українському і російському пошуку, по 2 прогони;
  - запис у `docs/prom_marker_experiment_log.tsv`;
  - запуск: `venv/bin/python tools/prom_marker_check.py`.
- **Чи імпортовано:** `tools/prom_marker_check.py --api` на сервері.
  - Для групи RU маркер видно в API `keywords`.
  - Для групи UA ознака лише `date_modified`, бо українських ключів API не віддає.

## Як читати результат

| Імпорт | Маркер знайдено | Висновок |
|---|---|---|
| так | в основному блоці | ключі індексуються повноцінно |
| так | лише в частковому блоці | ключі працюють як «друга частина видачі» (як у документації) |
| так | ніде, кілька днів поспіль | ключі цього поля пошук не використовує |
| ні | — | тест нічого не показує, чекати імпорту |

Порівняння UA з RU показує, чи є різниця між мовами.

**Уточнення чату 15.09:**
- **Дата зміни в API — лише ознака імпорту.** Вона каже «Prom забрав
  новий вміст картки», але не «слово індексується пошуком». Навіть поле
  `keywords` в API для групи RU доводить лише, що дані дійшли. Висновок
  про індексацію ключів, для UA і для RU, — **лише** за браузерним пошуком
  маркера (обидва блоки видачі).
- **Рішення за результатом — не бінарне.** Ранг магазину виміряно як
  сильніший ефект: 2/178 при ~32, 40 товарів. Тому:
  - маркер знайдено → ключі індексуються, але це другорядний важіль.
    Партію 6 робимо з нижчим пріоритетом, головне — ранг (покази,
    замовлення, відгуки, ProSale);
  - маркер не знайдено кілька днів → ключі цього поля пошук не
    використовує. Партію 6 не робимо, усі зусилля — на ранг і назви.

## Журнал

- **15.09 19:42 — опубліковано** (`noire_prom.xml` на GitHub, 5361 офферів).
  Звірено з опублікованим файлом: «зорвінтал» у `keywords_ua` 50/50,
  «квербаліс» у `keywords` 50/50; поза задуманими картками й полями
  (назви, інше поле ключів) — 0. Разом із цією публікацією вийшли 5 змін
  категорій (варіант А і В): SO5957 → Бдсм-іграшки; SO9790, ZPMP02 →
  Екстендери; PJ10480 → Лубриканти; SO3509 → Збуджуючі засоби.
- **16.09 04:00–04:02 — перша перевірка. Маркери знайдено, але не на всіх картках.**

  | | група UA «зорвінтал» (`keywords_ua`) | група RU «квербаліс» (`keywords`) |
  |---|---|---|
  | імпорт (API, рос. ключі) | — (API укр. ключів не віддає) | **50/50** |
  | пошук ua, прогони 1 і 2 | 8/50 | 7/50 |
  | пошук ru, прогони 1 і 2 | 8/50 | 7/50 |
  | частковий блок | 0 | 0 |
  | усього карток у видачі | 8 | 9 |

  Контроль SO5178 пройдено (перевірка без нього не будується). **Усі 4
  прогони кожної групи дали той самий перелік SKU** — жодного мерехтіння,
  на відміну від звичайних запитів (43 % мигають).

### Висновки (В)

1. **Обидва поля ключів індексуються й шукаються.** Слово, якого немає в
   назві та описі, знаходить картки в **основному** блоці видачі, а не в
   частковому. Мова запиту значення не має: український і російський пошук
   дають однаковий перелік. Для `keywords_ua` це перший прямий доказ.
2. **Індексується не вся картка, а меншість.** Для групи RU API доводить,
   що маркер є в `keywords` **усіх 50** карток, а пошук показує **7**.
   Це запит без жодної конкуренції: слово вигадане, крім наших карток його
   ні в кого немає. Тобто 86 % наших карток не дістати з пошуку навіть
   унікальним словом із їхнього ж поля. Частка (14–16 %) збігається з
   базовою видимістю за точною назвою (9,5–14 %).
3. **Це не ефект рангу серед однакових пропозицій.** Тут конкурентів немає
   взагалі, і видача коротка (8–9 карток). Отже, крім рангу серед
   однакових пропозицій діє **другий, сильніший обмежувач: більшості наших
   карток у видачі немає взагалі**.

### Ознака, яку треба перевірити окремо (П)

Розвідка по шести ознаках картки (перестановочний тест медіан, 15 знайдених
проти 85): ціна 559 проти 1339 грн (p = 0,037), довжина опису 711 проти
1379 (p = 0,14), довжина ключів (p = 0,23), довжина назви (p = 0,60),
кількість характеристик (p = 0,49), кількість фото (p = 1,00). Розмір
категорії (p = 0,17), статус, наявність, варіативність, бренд і категорія —
без різниці.

**Жодна ознака не проходить поправку на шість порівнянь (поріг 0,0083).**
Ціна — єдиний кандидат. За цінними групами на тих самих 100 картках:
дешевша половина 12/50 = 24 %, дорожча 3/50 = 6 % (Фішер p = 0,023),
нижня чверть 8/26 = 31 %, **верхня чверть 0/25**.

Це post-hoc, на вибірці, де гіпотезу породжено, тому цифри йдуть у
планування, а не у висновок. Підтверджувальний протокол написано наперед:
`docs/prom_price_threshold_experiment_plan.md` (75 карток на групу за
розрахунком потужності, пари з однієї категорії, один основний тест).

**Що вже можна сказати:** повнота картки — характеристики, фото, довжина
ключів і назви — на потрапляння у видачу помітно не впливає. Масове
поліпшення карток не є шуканим важелем.

### Що це означає для роботи

- За правилом рішення (уточнення чату 15.09): **маркер знайдено → ключові
  слова працюють, але це другорядний важіль**. Партія 6 — з нижчим
  пріоритетом.
- Головне питання змінюється. Було: «чи враховує пошук ключі». Стало:
  **«чому 86 % наших карток відсутні у видачі навіть за унікальним
  словом»**. Це найсильніший аргумент для листа в підтримку Prom, бо його
  легко відтворити: один запит, наперед відомий перелік карток.

- **Далі:** повторити перевірку 17 і 18.09. Дивитись не лише на кількість, а
  на **склад** (`prom_marker_check.py --compare`, поріг задано наперед):
  збіг переліку ≥ 80 % → поріг потрапляння у видачу; менше → ротація
  видимості, інший механізм. Потім `"active": false` і прибрати маркери.
