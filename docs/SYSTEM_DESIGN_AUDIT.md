## Слабкі місця — за пріоритетом

### 1. Нема резервних копій бази — ризик втрати даних (КРИТИЧНО)
Postgres (`agent_postgres`, 262 МБ: замовлення, каталоги, переклади, мапінги категорій,
історія цін) лежить у `/home/tek/agent-data/postgres_data` на **єдиному диску єдиного
сервера**. У crontab немає жодного `pg_dump`, файлів дампів на диску не знайдено.
Збій диска = втрата тижнів ручної роботи (переклади TOPTUL, мапінги Епіцентру).
**Пропозиція:** щоденний `pg_dump -Fc` о 04:00 у `~/backups/pg/` з ротацією 14 днів +
копія **з сервера на ноутбук** (через Tailscale, `rsync`), бо копія на тому ж диску від
збою диска не рятує. Персональні дані покупців — тому **не** в GitHub.
Щомісячна перевірка відновлення (`pg_restore` у тимчасову БД) — бекап без перевірки
відновлення не рахується.
*Потрібен дозвіл власника: зміна crontab.*

### 2. Одна машина — єдина точка відмови (ВИСОКИЙ, свідомий компроміс)
usa1: 3,8 ГБ пам'яті, усе на ній (БД, агенти, фіди, боти). Гаряча заміна для малого
бізнесу не виправдана, але потрібен **план холодного відновлення**: код — GitHub,
`.env` — зашифрована копія в власника, БД — пункт 1. Цільовий час відновлення — 2 год.
Документ-інструкція «що робити, якщо usa1 помер» — один раз.

### 3. Тихий збій Prom (ВИСОКИЙ, відомий з 16.09)
Агент замовлень Prom показує 401 як «нових замовлень немає». Саме той антипатерн, який
нові модулі вже не мають. **Пропозиція:** перевести агента на `integrations/prom.py`
(401 → тривога). *Потрібні новий ключ Prom і дозвіл на зміну агента.*

### 4. Хто стереже сторожа (СЕРЕДНІЙ)
Якщо впаде cron або сам `watchdog.py`, тривог просто не буде — тиша виглядає як «усе
добре». **Пропозиція:** ранковий звіт бота-помічника (TASK-07) щодня о 9:00 — це і є
«пульс»: нема звіту → щось зламалось. Додати в звіт вік останнього прогону сторожа.

### 5. Лише одна копія коду сервера між пушами (НИЗЬКИЙ)
Сервер автокомітить без push. Станом на 19.09 невідправлених комітів 0, але механізм
дозволяє накопичення. Сторож уже перевіряє git — додати поріг «> 0 невідправлених > 24 год».

### 6. Зайві компоненти (НИЗЬКИЙ)
n8n на сервері — 270 МБ пам'яті з 3,8 ГБ; qdrant/redis — використовують лише старі
агенти `efficiency/dev/finance`. Кожен компонент — ще одна точка збою й поверхня атаки.
Рішення за власником (n8n він хоче зберегти).
