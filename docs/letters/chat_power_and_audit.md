# Відповідь: метод розрахунку n і аудит замірів до виправлення

## 1. Розрахунок n — ви праві в підозрі, і жоден із двох наших не правильний

Мій був **(б)**: пряме обчислення точного критерію Фішера за припущення, що
спостережені частки 16 % / 4 % втримаються на більшій вибірці. Тобто це n,
за якого **точкова оцінка ледь перетинає поріг**, а не n, за якого ефект буде
виявлено з заданою ймовірністю. Ваш діагноз точний.

Але ваш (а) теж не дає 80 % потужності. Перевірив симуляцією саме того
критерію, яким я збираюсь міряти:

```
h Коена = 0.4203
(а) асимптотика, 80 %          →  44 на групу     ← ваш
(б) частки дають p<0.05        →  75 на групу     ← мій

(в) ТОЧНА потужність Фішера, симуляція 4000 повторів:
     n= 45 → 34 %
     n= 60 → 48 %
     n= 75 → 62 %     ← ось чому мої 75 «спрацювали»: це 62 %, не 80 %
     n= 90 → 74 %
     n=110 → 82 %     ← мінімум для 80 %
     n=130 → 89 %
```

Причина розбіжності саме та, яку ви припустили як одну з двох: формула Коена
асимптотична й антиконсервативна на малих частках (4 %) і помірних n, а точний
критерій Фішера дискретний і консервативний. Симуляція знімає питання —
вона рахує потужність того критерію, який реально застосовується.

**Робоче число: 110 карток на групу, 220 запитів, ~2 години в один потік.**

Код розрахунку (щоб звірили):

```python
def fisher(a,b,c,d):                    # двобічний точний
    n=a+b+c+d
    def p(x): return comb(a+b,x)*comb(c+d,a+c-x)/comb(n,a+c)
    p0=p(a)
    return sum(p(x) for x in range(max(0,a+c-(c+d)), min(a+b,a+c)+1)
               if p(x)<=p0+1e-12)

for n in (45,60,75,90,110,130):         # потужність
    ok=sum(fisher(a:=sum(random.random()<.16 for _ in range(n)), n-a,
                  c:=sum(random.random()<.04 for _ in range(n)), n-c) < .05
           for _ in range(4000))
```

## 2. Аудит: які заміри зроблені до виправлення

Виправлення екстрактора датоване 13:59. За часом створення скриптів:

| Замір | Час | Стан |
|---|---|---|
| 12 карток, перший прогін | 08:50 | **до виправлення** |
| 12 карток, повтор | 13:09 | **до виправлення** |
| 40 карток, режим `name` | 13:14 | **до виправлення** |
| 33 картки, обрізаний запит | 13:25 | **до виправлення** |
| широкий запит (ваш пункт 1) | 13:57 | **до виправлення** |
| 40 карток, `name_fixed` | 13:59 | виправлений |
| довжина назви, 25+25 | 14:13 | виправлений |

**Одне уточнення до вашої ознаки підозри.** Мала кількість продавців на
сторінці сама по собі бага не доводить: у **виправленому** прогоні теж
12 із 40 рядків мають `results` від 1 до 9, і це справжня остання сторінка
короткої видачі. Розрізняє не число, а дата. У виправленому коді я додав
пряму самоперевірку — лічильник сторінок, де кількість товарів не дорівнює
кількості продавців; у прогоні `name_fixed` він дав **0**.

Обидва замічені заміри перезапускаються виправленим кодом просто зараз —
це повторний парсинг, live-дані не змінюються, вашого чи власникового
дозволу не потребує.

## 3. Ваші відповіді прийняті — як вони лягають у план

**Не змішувати прибирання хвоста «…, силікон» із тестом довжини.** Прийнято,
і це саме та помилка, яку я міг зробити: обидві зміни чіпають назву, ефект
став би нероздільним. Розводжу в часі й по різних підкатегоріях.

**Метрика — % знайдених власним парсингом із контролем щоразу.** Приймаю з
вашим застереженням: це проксі присутності, не факт про ранжування. Записую
саме так, щоб через місяць ніхто не прочитав це як «метрика продажів».

**Контрольна група.** Ваше зауваження про внутрішню конкуренцію суттєве:
тест і контроль з однієї підкатегорії того самого продавця змагаються за той
самий пул позицій. Беру ваш другий варіант — рахувати **% знайдених по
категорії загалом**, а не позицію окремої картки. Він стійкіший до
перерозподілу всередині магазину.

**Маркерний експеримент першим.** Погоджуюсь логічно: без часу переіндексації
каданс будь-якого A/B вгадується. Але виконати не можу — це зміна живих
карток, рішення власника. Пункт лишається в черзі до нього, і я не буду
проектувати A/B, доки цього числа немає.
