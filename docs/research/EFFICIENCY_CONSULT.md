# Зовнішня консультація з ефективності: що сказав Gemini і що з цього правда

**Дата:** 21.09.2026. **Запит власника:** «дай Gemini роль спеціаліста з ефективності,
опиши архітектуру, постав усі питання; потім те саме спитаємо в Codex і порівняємо».
**Метод:** одне питання (686 слів: архітектура + 8 питань) двом моделям Gemini —
`gemini-flash-lite-latest` і `gemini-3-flash-preview`. Промпт: `docs/research/efficiency_prompt.md`.

## 1. Чому це варто робити саме так

Кожну пораду перевіряю по нашій системі. Нижче — розділення на три купи:
**підтверджено** (перевірив фактом), **помилка** (суперечить нашим даним),
**неперевірне** (звучить розумно, але доказу нема). Без цього консультація — просто думка.

## 2. Що обидві моделі сказали однаково (і це збігається з практикою)

| Теза | Наш стан |
|---|---|
| Детерміновану логіку (парсинг, арифметика, SQL) взагалі не давати LLM | уже так: `research/`, `content/` — чистий код із тестами |
| Головному агенту не читати повні логи й не робити `grep` руками | частково: довгі виводи досі потрапляють у контекст |
| Довгий вивід — у файл, у контекст лише статус і 5 рядків помилки | **не зроблено**, найбільший запас |
| Завдання робітнику = контракт: контекст + інваріанти + шляхи + незмінні тести | уже так (`docs/tasks/TASK-NN.md` + `tests/`) |
| Перехресну перевірку застосовувати лише до архітектурних рішень | згоден: на дрібницях це подвійна витрата |

## 3. Підтверджено фактом — і вже впроваджено

**Порада (сильніша модель, п. 5):** «додайте в ТЗ вимогу: спочатку запусти тести на
поточному коді, переконайся, що вони падають саме там, де треба».

Перевірив: у запускачі `scripts/codex_task.py` **не було** прогону перевірок до старту
(`grep -c baseline` → 0). Саме через це 20.09 на TASK-26 згоріли три спроби: у дереві
лежали тести майбутнього завдання без модуля, і падала не робота Codex, а чуже.

Зробив `baseline()`: перед запуском виконуються ті команди перевірки, що містять
`-k 'not …'` («решта тестів»), і якщо вони падають — Codex не стартує.
**Перевірка одразу знайшла ще один справжній дефект:** тест
`test_orders_search_filters_by_status_group[виконані замовлення вчора]` падав сьогодні,
бо дата замовлення була зашита як `2026-09-19`. Тобто тест був зелений рівно один день.
Виправлено: дата рахується під час запуску.

Один прогін консультації → одна вада процесу й одна вада тестів. Це окупилось одразу.

## 4. Помилки консультанта (і чому важливо було перевірити)

| Твердження | Чому неправда |
|---|---|
| «Каталог 95 скілів вантажиться в кожну сесію й з'їдатиме контекст» (flash-lite, п. 8.1) | навпаки: каталог **не** автозавантажується, у сесію йде лише опис router-скіла на 43 рядки. Її ж «виправлення» — це те, що ми вже зробили вчора |
| «Додайте прогін повного пакета старих тестів перед прийняттям» (flash-lite, п. 8.3) | уже є: друга команда перевірки — завжди повний пакет |
| «14 скілів, коли стане 50, з'їдять 20 % контексту» (flash-3, п. 8.1) | рахунок не сходиться: 14 скілів = 7,5 КБ описів, 50 ≈ 27 КБ ≈ 7 тис. токенів. Це одиниці відсотків, не 20 % |
| «Економія токенів Opus на 30–40 %» (flash-lite, п. 2) | число взяте зі стелі, підстав не наведено |
| «Пропустіть завдання через Ollama `qwen2.5:7b` для пошуку суперечностей» (flash-lite, п. 5) | суперечить перевіреному: ця модель непридатна для українських текстів. Сильніша модель у тому самому питанні порадила **Gemini** — і це правильно |
| «Файлова памʼять без індексації» (flash-3, п. 8.3) | індекс є: `MEMORY.md`, 31 запис, вантажиться щосесії |

**Висновок про метод:** слабша модель помилилась тричі саме там, де вигадувала стан нашої
системи замість того, щоб сказати «не знаю». Сильніша модель була обережніша й прямо
написала «не знаю» про ліміти Codex. **Перевіряти треба кожну тезу про нас.**

## 6. Відхилено

- **«Прочитай CURRENT_STATE.md і забудь історію»** (flash-3, п. 4) — у нас уже є памʼять
  і `docs/research/`; ще один файл стану дублюватиме їх і розходитиметься з ними.
- **Метрика «токенів на модуль»** — Claude Code не дає нам розбивки токенів на завдання,
  рахувати нічим. Беремо натомість спроби й частку з першої спроби.
- **Перевірка суперечностей локальною Ollama** — див. §4.

## 7. Наступний крок

Те саме питання поставити Codex і звірити три відповіді. Цінність не в «двох думках»,
а в тому, що кожна модель вигадує **різні** речі про нашу систему — а спільне в їхніх
відповідях із більшою ймовірністю правда.
