### 1. РОЗПОДІЛ РОБОТИ (Дерево рішень)

Щоб мінімізувати витрати Opus, використовуйте таку логіку:

1.  **Це детермінована операція?** (Парсинг відомого формату, розрахунок ціни, перейменування файлів, міграція БД за схемою).
    *   **Рішення:** Пишемо скрипт (Python/Bash) один раз. **Не давати LLM.**
2.  **Це масова обробка слабкоструктурованих даних?** (Описи товарів, витягування характеристик з тексту, класифікація 1000+ позицій).
    *   **Рішення:** **Gemini (Flash/Pro)** через API або Studio.
3.  **Це реалізація ізольованої функції/модуля за готовим ТЗ?** (Написати метод, покрити тестами існуючий інтерфейс).
    *   **Рішення:** **Codex CLI.**
4.  **Це зміна архітектури, пошук багу в логіці взаємодії модулів або планування нового функціоналу?**
    *   **Рішення:** **Claude Code (Opus).**

**Вирішальна ознака:** Рівень невизначеності. Якщо вхід (ТЗ) і вихід (Тести) чітко визначені — це робота для Codex. Якщо треба вирішити «як саме це має працювати» — це Claude.

### 2. ЧОГО НЕ ВАРТО РОБИТИ ГОЛОВНОМУ АГЕНТУ

*   **Читання повних логів тестів:** Якщо тести впали, Claude не має читати 200 рядків виводу. Скрипт-запускач має віддавати йому лише назву тесту, що впав, і конкретний `AssertionError`.
*   **Форматування тексту/JSON:** Не просіть Claude «причесати» масив даних. Це робота для Gemini або локального скрипта.
*   **Пошук по файлах (grep):** Не дозволяйте Claude перебирати файли в пошуку рядка. Він має викликати інструмент пошуку, отримати список імен файлів і лише потім читати потрібний.
*   **Написання Boilerplate-коду:** Створення стандартних CRUD-методів — це витрата Opus. Це має робити Codex за шаблоном.

### 3. ВИВІД ІНСТРУМЕНТІВ (Економія контексту)

Довгий вивід — головний «пожирач» грошей.
*   **Прийом «Head/Tail/Grep»:** Створіть wrapper-скрипт для читання логів. Замість `cat log.txt` агент має викликати `read_log --errors-only` або `read_log --tail 50`.
*   **Тимчасові артефакти:** Якщо вивід інструменту (наприклад, SQL-дамп структури) великий, скрипт має зберігати його у файл `temp/schema.txt`, а Claude віддавати лише: «Схема збережена, в ній 150 таблиць, які поля вас цікавлять?».
*   **Диференціальний вивід:** При запуску тестів показуйте Claude лише **різницю** між попереднім і поточним запуском (що саме зламалося/полагодилося).

### 4. ПАМʼЯТЬ І СТИСНЕННЯ

Автостиснення Claude Code часто працює як «чорна скринька».
*   **Рішення:** Впровадьте файл `docs/context/CURRENT_STATE.md`.
*   **Механіка:** В кінці кожної сесії Claude **зобов'язаний** оновити цей файл: що зроблено, на чому зупинилися, які ключові рішення прийняті.
*   **Ефект:** На початку нової сесії ви даєте команду: «Прочитай CURRENT_STATE.md і забудь історію». Це очищує контекст від сміття (спроб, помилок, довгих лістингів), залишаючи лише «сухий залишок».

### 5. ПИСЬМОВІ ЗАВДАННЯ ДЛЯ РОБІТНИКА

*   **Шаблон «Контракт»:** Завдання для Codex має містити секцію `INVARIANTS` (що не можна змінювати ні за яких умов).
*   **Дешева перевірка (Pre-flight):** Перед запуском Codex, віддайте текст завдання **Gemini** з промптом: «Знайди суперечності між ТЗ і тестами. Чи достатньо інформації, щоб написати код без уточнень?». Це коштує 0 токенів на безкоштовному тарифі й економить час Codex.
*   **Припущення:** Я припускаю, що ваші тести — це `pytest` або аналог. Якщо так, додайте в ТЗ обов'язкову вимогу до Codex: «Спочатку запусти тести на поточному коді, переконайся, що вони падають саме там, де треба».

### 6. ПЕРЕХРЕСНА ПЕРЕВІРКА МОДЕЛЕЙ

Щоб це не було просто «дві думки», використовуйте **Метод Адвоката Диявола**:
1.  Claude генерує рішення.
2.  Ви копіюєте рішення в Gemini/Codex із запитом: «Це рішення від Claude. Знайди в ньому 3 критичні вразливості або сценарії, де воно зламає базу Postgres при 10к товарів».
3.  **Порівняння:** Ви шукаєте не «хто правий», а чи зміг другий агент знайти реальний edge case (наприклад, дедлок при оновленні залишків).

### 7. ЩО ВИМІРЮВАТИ (KPI)

1.  **Token-to-Commit Ratio:** Скільки токенів Opus витрачено на один успішний коміт (merge у main). Рахується через білінг Claude та `git rev-list --count`.
2.  **First-Pass Success Rate (Codex):** % завдань, які Codex виконав з першої спроби (без вичерпання 3 лімітів). Якщо падає нижче 80% — проблема в якості ТЗ від Claude.
3.  **Context Bloat Speed:** На скільки КБ зростає середня сесія Claude до моменту автостиснення.
4.  **Task Leakage:** Кількість разів, коли Claude довелося самому писати код, бо Codex не впорався.

### 8. ПОМИЛКИ АРХІТЕКТУРИ

1.  **Відсутність версіонування скілів:** Ви вантажите 14 скілів у кожну сесію. Коли їх стане 50, вони з'їдять 20% контексту просто «на вході». **Наслідок:** Opus почне тупити на складних задачах через перевантаження інструкціями.
2.  **Claude як єдиний «приймальник»:** Ви дивитесь код очима, але Claude робить коміт. Це створює ілюзію контролю. **Наслідок:** Коли база виросте до 100к товарів, Claude може пропустити неефективний SQL-запит (N+1), бо він фокусується на логіці ТЗ, а не на продуктивності БД.
3.  **Файлова пам'ять без індексації:** 30 файлів-фактів — це межа для лінійного читання. **Наслідок:** Скоро Claude почне плутати факти з різних файлів або ігнорувати частину з них. Потрібна структура (наприклад, один `MAP.md`, який посилається на інші).

**Не знаю:** Я не знаю точних лімітів вашого «добового запобіжника» для Codex, тому не можу сказати, чи витримає він паралельну роботу над 3+ модулями одночасно.

**Припущення:** Я припускаю, що ваша Postgres база не має складних тригерів або процедур, які виконуються поза кодом Python, інакше Codex не зможе їх протестувати в пісочниці.
