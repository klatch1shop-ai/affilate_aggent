# Система задач через провайдерів — дослідження й план

**Дата:** 26.09.2026. **Привід:** дві довгі паралельні задачі (Епіцентр і Розетка)
та потреба виконувати їх через різних провайдерів, з переходом на безкоштовні,
коли Codex недоступний, і з контролем доступності моделей.

---

## 1. Головний висновок: це НЕ дві однакові задачі

Припущення було, що на Розетці ~1100 карток «не пройшли модерацію» — тобто така
сама робота з атрибутами, як на Епіцентрі. **Це не так.** Перевірка живим API
показала інше.

### Що насправді на Розетці

Лічильники по джерелах (`/goods/{tab}`, 26.09):

| джерело | модерація | помилки | приховані | у продажу |
|---|---|---|---|---|
| dropoffice | **1103** | 0 | 0 | **0** |
| toptul | 5823 | 0 | 8 | 129 |
| noire | 0 | 0 | 964 | 3183 |
| carvol | 0 | 0 | 67 | 8177 |

Зібрано 1077 із 1103 карток dropoffice. **Усі до одної** мають:

- `upload_status_title` = «Підготовлений»
- `error_type`, `error_reason`, `blocked_reason` — **порожні**
- стоп-бренди / стоп-категорії / стоп-слова — **не спрацювали**
- `photo` = `[]`, `photo_upload_status` = 0
- `available` = 0, `stock_quantity` = 0

**Тобто їх ніхто не відхиляв.** Немає жодної причини відмови — вони просто
ніколи не були оброблені.

Перевірено й решту місць, де причина могла б бути (питання власника 26.09):

- `comment` — порожній в усіх 1077;
- `changes.reasons` — порожній список в усіх;
- `rz_status`, `rz_sell_status`, `change_status`, `docket` — усі `None`, тобто
  Rozetka цим карткам статусу **взагалі не присвоювала**;
- повідомлення модерації (`msgType` = goods / items / moderation) — 0 записів.

**Зачіпка для кабінету:** усі 1077 належать лише **двом заявкам** —
`bpm_number` 4602797 (961 картка) і 4602798 (97). Тобто вони подані пакетом і
стоять у черзі цих двох заявок. Саме їхній стан варто глянути в кабінеті.

### Чому це не задача для моделей

Перевірив ланцюжок постачання по одній ланці за раз:

1. **Фід існує й здоровий.** `output/dropoffice_rozetka.xml`, 1108 оферів,
   `<picture>` у **всіх 1108**, назви українською (`name_ua`), 980 з
   `available="true"`, реальні залишки.
2. **Фото доступні ззовні.** 5 URL із фіду → HTTP 200, справжні JPEG 130–550 КБ.
   (Гіпотеза «кабінетні посилання закриті» — не підтвердилась.)
3. **Фід опублікований і свіжий.** `noire-feed/dropoffice_rozetka.xml`, 17 МБ,
   останній коміт **сьогодні 12:25**, фото в опублікованій версії на місці.
   (Гіпотеза «не публікується» — теж не підтвердилась.)

Порівняння, яке вирішує питання: картки **noire, що успішно продаються**
(3183 шт.), мають так само порожній `description_ua` — отже порожній
український опис **не є блокером**. Єдина відмінність dropoffice — `photo = []`
при тому, що у фіді фото є.

**Висновок:** фід у порядку, а Rozetka його для джерела 55861 не забирає.
Це налаштування кабінету (прив'язка фіду до джерела / активація джерела), а не
робота для LLM. **Жодна кількість провайдерів цього не виправить** — вони лише
спалили б квоту. Потрібна перевірка кабінету власником.

> Залишок для окремого розгляду: **noire — 964 приховані** картки. Це вже може
> бути змістовна задача, але спершу треба глянути причину, а не припускати.

### Що справді є задачею для моделей

Лише Епіцентр:

- **405 карток** не оброблено (1385 з 1790);
- **2426 рядків** мають «перевірку», де обидва джерела — одна модель
  (94% від 2557), їх треба перепровірити справжнім другим вендором;
- 131 рядок перевірено чесно — їх чіпати не треба.

## 2. Що вже зроблено сьогодні

- `shared/utils/vendor_pool.py` — вендор як іменована річ: `verdict()` не має
  права сказати «ЗБІГ» при однаковому вендорі, `pick_two()` бере друге джерело
  в іншого вендора, `Stats` рахує відповіді/збої/час. 20 тестів.
- `call_groq` / `call_cerebras` / `call_openrouter` у `llm_router`, з фото для
  OpenRouter. Поза дефолтним `CHAIN` — вмикаються свідомо.
- `tools/gemini_quota_probe.py` — коли скидається добова квота Gemini
  (опівночі PT = 10:00 Київ).

### Заміряна придатність вендорів (не думка, а прогін)

Ті самі рядки, що раніше провалились, три вендори:

| вендор | відповів | медіана | що казав |
|---|---|---|---|
| openrouter | 2/3 | 50 с | **«2»**, **«розовий»** — єдиний, хто читає фото |
| gemini | 3/3 | 0,8 с | НЕ ВИДНО (усі) |
| codex | 3/3 | 4,4 с | НЕ ВИДНО (усі) |

Два уроки:
- **Швидкість ≠ користь.** Gemini відповідає за секунду, але не відповідає по суті.
- OpenRouter повільний (12–50 с), раз віддав порожнє, і пише **«розовий»**
  замість «рожевий» — російська форма. Епіцентр вимагає української, тож його
  відповіді потребують мовної перевірки.

## 3. План системи

Будується на `vendor_pool`, який уже є. Чотири частини.

### 3.1. Черга задач — довговічна

**Урок дня:** вартовий жив у `/tmp` і зник при вимкненні ноутбука; стан роботи
жив у контексті розмови й зникав при обриві.

Черга — файл у репозиторії (JSONL) або SQLite, з полями:
`id, kind, payload, state, attempts, vendor_a, vendor_b, answer_a, answer_b,
verdict, error, updated_at`.

Правила: кожен запис оновлюється одразу після відповіді (не пачками);
перезапуск підхоплює з місця; стан `в роботі` з давнім `updated_at`
повертається в `нова` автоматично.

### 3.2. Нагляд за доступністю — і за **придатністю**

Окремо два поняття, бо сьогодні вони розійшлись:

- **живий** — вендор відповідає на дешеву пробу;
- **придатний** — вендор дає змістовні відповіді **на цей тип задачі**
  (частка не-«НЕ ВИДНО» на останніх N рядках).

Реєстр стану: `вендор → {живий, квота_до, придатність_по_типу, медіана_мс}`.
Квоту з відомим часом скидання (Gemini — опівночі PT) не перепитуємо до строку.

### 3.3. Виконавець

Цикл на одну задачу:

1. взяти вендорів, які зараз живі й придатні для типу задачі;
2. `pick_two()` → два **різні** вендори (перший уміє фото);
3. виконати, записати обидві відповіді **разом із іменами вендорів**;
4. `verdict()` — чесний вердикт;
5. якщо живий лише один вендор — записати `НЕ ПЕРЕВІРЕНО (одне джерело)`,
   а не вдавати перевірку;
6. збої не ковтати — писати причину в `error`.

Порядок вендорів для Епіцентру за сьогоднішніми замірами:
фото — `openrouter` → `codex` → `gemini`; текст — `groq` → `cerebras` → решта.

### 3.4. Дошка й контроль

`docs/BOARD.md`, який **перегенеровує скрипт** із реальних джерел (черга, лог,
git, проби квот) — руками числа не вписуються. Показує не лічильник, а:

- скільки зроблено / скільки лишилось;
- **скільки перевірено двома різними вендорами** (головне число);
- що зараз блокує і до якого часу;
- стан кожного вендора;
- наступна дія.

Одна команда шле зведення в Telegram (`tools/notify_owner.py` — вже працює).

## 4. Порядок робіт

1. **Спитати власника про кабінет Розетки** — чи прив'язаний фід
   `dropoffice_rozetka.xml` до джерела 55861. Це розблоковує 1103 картки без
   жодної моделі. *(дія власника)*
2. Черга задач + дошка (п. 3.1, 3.4).
3. Нагляд за доступністю й придатністю (3.2).
4. Виконавець (3.3), перший прогін — **131 чесно перевірений рядок не чіпати**,
   починати з 405 необроблених.
5. Перепровірка 2426 рядків справжнім другим вендором.
6. Окремо подивитись 964 приховані картки noire — спершу причину.

## 5. Чого свідомо НЕ робимо

- Не кидаємо провайдерів на Розетку, поки не перевірено кабінет: причина там
  не змістова, і квота згорить намарно.
- Не рахуємо «ЗБІГ» від одного вендора — саме це знецінило попередній прогін.
- Не тримаємо стан у `/tmp`.
