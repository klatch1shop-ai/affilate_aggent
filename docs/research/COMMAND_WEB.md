## Як відрізняли «метод є» від «методу немає»

Кожен канал відповідає по-своєму, тому для кожного знайдено **відʼємний
контроль** — свідомо вигаданий шлях, і все, що відповідає так само, як він,
вважається відсутнім.

| канал | відповідь на вигаданий шлях | що це означає |
|---|---|---|
| Rozetka | HTTP **200**, `{'code': 5404, 'message': 'not_found'}` | 200 ≠ метод існує; дивитись у `errors` |
| Єпіцентр | HTTP 404, `{"message":"No route configured"}` | а от `entity.not_found` означає, що метод Є |
| Нова Пошта | HTTP 200, `success: false`, текст у `errors` | розрізняти «немає методу» і «бракує параметра» |
| Prom | HTTP 404 | звичайна поведінка |

Без цього контролю Rozetka дала б «працюють 12 з 12», хоча насправді чотири.

## Схема бекенду

Скелет — `core/actions.py`. Чотири шари, знизу вгору:

```
голос → розпізнавання → НАМІР
                          ↓
                    plan_from_text()        ← заготовка компілятора
                          ↓
                   ПЛАН: [крок, крок, …]    ← показується користувачу ДО виконання
                          ↓
                    REGISTRY[дія]           ← контракт: канали, параметри,
                          ↓                   оборотність, чи коштує грошей
                   адаптер каналу           ← перевірений метод API
```

### Чому саме так

**Дія, а не скрипт.** Зараз кожна операція написана окремо під кожен канал —
понад 60 файлів `tools/*`. Дія описує, ЩО робимо; канал — лише спосіб.
Порожня клітинка матриці одразу видно як дірку.

**Холостий прогін за замовчуванням.** Справжнє виконання вмикається явно
(`--execute`). Голос двозначний, і неправильно розпізнаний намір не має права
змінити ціну чи скасувати замовлення. Незворотні дії (`reversible=False`)
позначаються в плані попередженням.

**План показується до виконання.** Користувач бачить послідовність кроків
раніше, ніж щось станеться.

**Доступи — явна помилка, не виняток.** `.env` сервера й ноутбука різні
(03.10: на сервері немає `EPICENTR_EMAIL`, і зведення падало незрозумілим
`KeyError`). Тепер дія каже, якого саме ключа бракує.

### Чого свідомо НЕ зроблено

Спільний шар над усіма 60 скриптами **не будувався**. Перехресне обговорення
03.10 цю гіпотезу зламало: Codex показав, що запропонований критерій
перевірки нічого не розрізняє (рахував частку коду, а твердження було про

**контролю обовʼязкових синхронізацій**. Натомість зроблено

Гіпотеза лишилась у реєстрі (`tools/hypotheses.py`, H9) з правильним

### Виправлення 04.10: залишки Prom МОЖНА міняти через API

У таблиці «Дірки між каналами» вище стоїть «оновити залишки — лише фідом».
**Це неправильно.** Перевірено зворотною зміною на справжньому товарі SO5912:

```
POST /products/edit               {"id":3218833892,"quantity_in_stock":6}  → 5→6, читанням підтверджено
POST /products/edit_by_external_id {"id":"SO5912","quantity_in_stock":7}   → 5→7, потім повернуто 5
```

Обидва віддають `processed_ids` з нашим ідентифікатором. `edit_by_external_id`
приймає наш артикул, тому внутрішній номер Prom знати не треба.

Чому помилка трималась: ідемпотентна спроба (те саме значення) віддає
`processed_ids: []` без помилок — виглядає як відмова, хоча це просто «нема
чого міняти». Перевіряти треба ЗМІНОЮ значення, а не повтором наявного.

Наслідок: товар знімається з продажу одразу, а не чекає нічного імпорту.
Підключено командою `наявність <артикул> немає` / `кількість <артикул> N`.
