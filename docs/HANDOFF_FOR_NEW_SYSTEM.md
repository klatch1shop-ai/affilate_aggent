## 2. Що це за система

Мультиагентна система для **дропшипінгу**: товар лежить у постачальника,
магазин продає його на маркетплейсах, постачальник відвантажує покупцю.
Система автоматизує все між фідом постачальника й доставкою:

```
фід / XLS / API постачальника
  → нормалізація в PostgreSQL
    → мапінг категорій і характеристик під кожен майданчик
      → генератор фіду майданчика (XML) + валідатори
        → публікація (GitHub raw URL або API майданчика) + доказ публікації
          → модерація майданчика → реєстр зауважень → виправлення
            → замовлення: агент бачить нове → перевіряє наявність у постачальника
              → ТТН Нової Пошти → номер ТТН у майданчик
                → замовлення в CRM постачальника з ТТН → Telegram власнику
```

Масштаб на 15.09.2026:

| Постачальник | Товари | Майданчики |
|---|---|---|
| SexOpt (магазин NOIRE) | ~5 400 товарів, дві мови | Rozetka, Prom, Epicentr |
| TOPTUL (інструмент) | тисячі позицій | Epicentr, Rozetka |
| Carvol (автотовари) | — | Rozetka, Epicentr |
| Katran | — | Rozetka |
| dropoffice (будматеріали) | 1 103 оффери | Rozetka |

Хто працює: **власник** (рішення, капча, оплата постачальнику, спілкування з
менеджерами) і **агент Claude Code** (код, заміри, генерація, публікація,
перевірки). Додатково є «чат», тобто окрема LLM-сесія, яка рецензує
методологію замірів перед листами в підтримку. Агент пише їй листи в `docs/chat_letter_*.md`.

## 3. Архітектура й інфраструктура

### 3.1. Дві машини і GitHub

| Машина | Роль |
|---|---|
| **Ноутбук** (розробка) | код, експерименти, браузерні перевірки (Camoufox/Playwright), Ollama локально |
| **Сервер** (прод, Linux, користувач `tek`) | cron-синхронізації, генерація й публікація фідів, агенти замовлень (systemd), Telegram-бот, PostgreSQL / Redis / Qdrant у Docker |
| **GitHub `affilate_aggent`** | **єдина історія коду.** Ноутбук: `git pull` перед роботою, push після. Сервер: `watchdog` щогодини **автокомітить** зміни локально, без push |
| **GitHub `noire-feed`** | лише фіди. Публікація: коміт → `amend` → `push --force` під lock, щоб репо не розростався. `raw.githubusercontent.com` — URL для кабінетів |

**Пастка автокоміту.** Watchdog сервера комітить **будь-який** новий файл у
робочому дереві. Так у git двічі потрапило зайве: копія `.env` і тимчасовий
генератор. Правило: тимчасові файли на сервері створювати **лише в `/tmp`**,
а `.gitignore` тримати суворим (див. наш: `*.env`, `.env.*`, `*env_before*`,
`*.xml` з білим списком).

| Коли | Що |
|---|---|
| кожні 10 хв | `tools/watchdog.py`: здоров'я, автокоміт, перезапуск сервісів, свіжість фідів |

| 07:40 / 11:40 / 15:40 / 19:40 | `noire_stock_sync --publish-prom` (нічний імпорт Prom бере фід 19:40) |
| кожні 2 год, :25 | `noire_stock_sync --publish-epicentr-stock` |
| 07:00 | `agents/orders/feed_sync.py` (Epicentr) |
| 07:15 | `agents/orders/rozetka_github_sync.py` (Carvol → Rozetka) |
| 07:30 | `agents/orders/carvol_epicentr_sync.py` |
| 08:00 | `agents/orders/price_updater.py` |
| щомісяця | `git gc` у репо фідів |

**Кожен майданчик має свій генератор, свій файл і свій запис у cron.**
Оновлення одного не впливає на інші, тож перевіряти треба кожен окремо.

### 3.4. Сховища й моделі

- **PostgreSQL** — головне сховище товарів, мапінгів, цін, замовлень.
  Доступ через `shared/utils/db.py` (`psycopg2`, змінні `DB_*`).
- **Redis** — черги (`shared/utils/redis_queue.py`). **Qdrant** — векторна
  пам'ять (`shared/utils/memory.py`). Обидва опційні для конвеєра фідів.
- **LLM.** Anthropic API (`ANTHROPIC_API_KEY`) — основна модель. Ollama
  локально — дешеві допоміжні задачі. Досвід:
  `qwen2.5:7b` непридатна для українських текстів; `aya-expanse:8b` пише
  грамотно, але **вигадує характеристики**. Тому LLM ніколи не є джерелом
  фактів про товар, лише перекладу чи стилю під перевіркою.
- `docker-compose.yml` піднімає postgres, redis, qdrant, grafana, prometheus.

## 5. Конвеєр «постачальник → майданчик» (головна частина)

Порядок кроків не довільний: **спершу зрозуміти дані постачальника, потім
будувати мапінг, і лише потім писати генератор.** Зворотний порядок
означає переписування. Детально: `.claude/skills/SKILL-16-new-supplier-onboarding.md`
і `.claude/skills/SKILL-17-marketplace-pipeline.md`.

### 5.1. Аналіз джерела

- **Скільки джерел насправді.** У SexOpt виявилось три: XML українською
  (щодня), XLS з ціною й наявністю (кожні 2 год) і XML **російською**, який
  довго лежав невикористаним. Питати постачальника прямо: чи є фід іншою
  мовою, чи є окремий фід цін.
- **Семантика полів.** Наявність — це прапорець чи кількість? У SexOpt
  `available` — прапорець `'true'/''`, кількість лише в XLS. Ціна — це РРЦ,
  закупівля чи роздріб? У нас РРЦ, а закупівельної ціни немає; це
  з'ясувалося, коли знадобилась маржа.
- **Семантика фідів різних постачальників різна.** Carvol і TOPTUL по-різному
  позначають «немає в наявності». Агент замовлень має розрізняти **три стани**:
  є / немає / невідомо. «Невідомо» ніколи не означає «немає» (SKILL-19).
- Кодування, дублікати SKU, порожні описи, биті фото: зафіксувати до
  генератора.

### 5.2. Нормалізація

Одна таблиця товарів на постачальника в PostgreSQL з однаковими назвами
полів (`sku`, `name_ua`, `name_ru`, `price_rrp`, `available`, `quantity`,
`pictures`, `params`, `vendor`, `category_src`). Синхронізація за cron:
швидка (ціни й наявність) часто, повна раз на добу.

### 5.3. Мапінг категорій

- **Rozetka.** Категорію обирати за тим, де лежать **ті самі товари
  конкурентів**, а не за назвою категорії. Інструмент: `tools/rozetka_competitors.py`
  (пошук за артикулом без токена), SKILL-30.
- **Prom.** Правила «категорія постачальника + регулярний вираз за назвою →
  категорія Prom» у таблиці `prom_category_mapping` (перемагає найточніше
  правило). Фактичні категорії Prom (після його автокласифікації) знято
  знімком `prom_actual_category`. Урок 15.09: коли додаєте нове правило
  після знімка, воно має перекривати знімок (`created_at` > дати знімка),
  інакше правка не виходить. **Прибрати знімок повністю** погіршило б 26
  з 40 перевірених карток, тому це погана ідея.
- **Epicentr.** Категорії й набори атрибутів лише через PIM API
  (`epicentr_categories_fetch.py`, `epicentr_attrset_fetch.py`), мапінг —
  `epicentr_category_mapper.py` плюс ручне підтвердження.

### 5.4. Характеристики

- **Довідник майданчика замість карток конкурентів.** Беремо список
  параметрів і їхніх допустимих значень із API категорії (`rozetka_category_options.py`,
  набори атрибутів Epicentr). Тоді одиниці виміру, назви параметрів і
  значення точно ті, яких чекає майданчик (SKILL-17 §5б).
- **Ієрархія джерел значень** (SKILL-23): поле постачальника → назва товару
  (регулярні вирази) → опис постачальника → офіційний сайт виробника за
  **точним** збігом моделі. Чужа картка на маркетплейсі джерелом не є.
  **Здогадки заборонені**, краще порожнє поле.
- **Одиниці.** Числові параметри мають одиницю з довідника категорії
  (`«Товщина: 5 мм»`, а не `«5»`). Це було зауваження Rozetka до dropoffice.
- **Внутрішня узгодженість.** Назва, параметри й опис не повинні
  суперечити одне одному (152,4 проти 152,5 мм; площа, що не дорівнює
  добутку розмірів). **Джерелом правди для розмірів є назва**, а
  параметри й опис вирівнюються під неї (`align_desc_sizes()`,
  `name_dims_mm()` у `dropoffice_rozetka_generator.py`).

### 5.5. Назви, описи, фото

- **Назва** за шаблоном категорії майданчика: тип + бренд + модель +
  ключова ознака. Prom обмежує назву 110 символами. Опечатки й гомогліфи
  (латиниця в кирилиці) чистить `homoglyph.py`.
- **Опис має бути лише про цю одиницю.** Rozetka відхиляє «розміри в
  асортименті», таблиці всіх розмірів, «на вибір». Генератор вирізає такі
  речення й блоки (`unit_only_description()`).
- **Унікальність.** Однаковий з іншими продавцями текст дає склеювання
  й програш у видачі. Замір дублів і унікалізацію описує SKILL-18.
- **Фото тільки з цим товаром.** Колажі «купують разом» і фото чужого
  варіанта відхиляються. Ручні заміни й винятки задаються у файлі
  override (приклад формату: `data/dropoffice_photo_override.json`, самі
  дані наші).
- **Дві мови симетричні.** Якщо заповнено `name_ua`, має бути й `name`;
  якщо є `keywords_ua`, мають бути й `keywords` (SKILL-17 §4).

### 5.6. Ціна

`tools/price_rules.py`: ціна = РРЦ × націнка за правилом (фід → категорія
→ артикул). Кожна зміна пишеться в історію з причиною. Перед застосуванням
показується diff і перевірка проти конкурентів. Антидемпінг-перевірка є в
`noire_stock_sync.check_antidumping()`. **Ціни й націнки не брати з нашого
`data/price_rules.json`**: це наші комерційні рішення.

### 5.7. Валідація: два незалежні шари

1. **Власний валідатор** (структура, ліміти, довідники, одиниці, симетрія
   мов) плюс скорер якості.
2. **Офіційний валідатор майданчика.** У Rozetka це
   `seller.rozetka.com.ua/gomer/pricevalidate/check/index`: посилання на фід,
   email і капча (капчу проходить людина). Звіт приходить листом від
   `gomer_services@rozetka.com.ua`. **Він ловить те, чого ми не знаємо**,
   бо правила майданчика змінюються без попередження.

Особливості валідатора Rozetka: `stock_quantity=0` при `available="false"`
— норма, а не помилка.

### 5.8. Публікація і правило «готово»

Зміна генератора чи фіду **не вважається завершеною**, поки не виконано всі
три перевірки (`CLAUDE.md`):

1. код **розгорнуто на сервері**, звідки публікує cron (а не лише зібрано
   на ноутбуці);
2. **MD5 генератора** на ноутбуці й сервері збігається;
3. **опублікований URL звірено з локальним файлом за хешем**. Дата в шапці
   фіду нічого не доводить: 10.08 вона оновлювалась щогодини, а cron
   збирав фід старим кодом, і менеджеру дали посилання на невиправлений файл.
   `raw.githubusercontent.com` кешує 5 хв, тому для точного доказу
   брати blob sha через `api.github.com/repos/<owner>/<repo>/contents/<file>`.

### 5.9. Модерація і реєстр зауважень

Кожне зауваження менеджера майданчика записується в реєстр
(`tools/moderator_findings.py`) і закривається **лише з доказом**. Статуси
розрізняють «проаналізовано» і «виправлено й опубліковано». Без реєстру два
зауваження Rozetka пролежали місяць і прийшли вдруге.

Для відповіді менеджеру пишеться аудит-скрипт, який рахує кожне зауваження
**і в нашому фіді, і в джерелі постачальника**, щоб бачити, що успадковано,
а що додав генератор. Приклад: `tools/dropoffice_rozetka_audit.py`,
результат dropoffice 15.09: асортимент 680 → 0, одиниці 973 → 3,
невідповідності 444 → 0.

## 6. Особливості майданчиків (перевірено практикою, не документацією)

| | Rozetka | Prom | Epicentr |
|---|---|---|---|
| Публікація | XML за URL | XML за URL (імпорт за розкладом) | PIM API / XML наявності |
| Назва | `name` + `name_ua` | `name` рос., `name_ua` укр., ≤110 | через PIM |
| Опис | `description_ua` | `description` + `description_ua` | через PIM |
| Пошукові слова | немає | `keywords` + `keywords_ua`, ≤1024 | немає |
| Складені значення | окремий тег | розділювач `\|` | — |
| Модерація | відділ адаптації, листи, заморожування картки | автоматична + ProSale | менеджер |

### 6.1. Rozetka

- Seller API: авторизація логін/пароль → токен (`shared/knowledge_base/rozetka/api_auth.md`).
  Статуси замовлень беруться з `/order-statuses/search`, а не з пам'яті.
- **ТТН у замовлення:** `PATCH /orders/{id}` з `{"status": 61, "ttn": "..."}`
  (61 = «Заплановано передачу перевізникові»). Після запису перевіряти
  **окремим GET**. ТТН буває в `ttn` або в `delivery.declaration_number`.
- Причини відмов модерації класифікує SKILL-29. Основні: асортимент в
  описі, фото, одиниці, невідповідність даних, категорія.
- Картка «заморожується» з моменту відправки на перевірку: зміни в фіді в
  цей час не видно менеджеру.

### 6.2. Prom

- `PROM_API_TOKEN`. Метод edit приймає лише `description` (рос.). Українську
  версію оновлює **тільки імпорт фіду**.
- **Графік імпорту:** денні імпорти оновлюють лише наявність і кількість;
  назви й ключові слова — тільки нічний (~01–03 Київ, бере фід 19:40).
  Тому ефект зміни назв видно не раніше ніж наступного ранку.
- **Пошук.** HTML видачі (`tools/prom_search.py`) бачить лише основний
  блок. Блок «часткові збіги» довантажує браузер, тому потрібен
  `prom_search_browser.py`. Збіг, розділений між назвою й ключовими
  словами, пошук не зараховує (є в документації Prom). Через це наші ранні
  тести ключових слів були некоректні.
- **Мерехтіння видачі:** ~43 % видимих карток то є, то немає. Кожен запит
  повторювати ≥2 рази, контрольний запит — з повторами до 3.
- **Ранг нового магазину.** У нас 0 відгуків і 1 замовлення. Серед
  однакових пропозицій різних продавців нашу показано 2 рази зі 178 при
  очікуваних ~32 (P ≈ 5·10⁻¹⁹). За власною точною назвою нашу картку
  показано в 30 % випадків, чужі — у 63 %. Висновок для нового магазину:
  **без замовлень і відгуків видимість на Prom буде низькою незалежно від
  якості карток.** Плануйте перші продажі й відгуки (ProSale, ціна,
  реклама) з першого дня.
- **Маркер-експеримент** — метод перевірити, чи індексується поле. У поле
  (напр. `keywords_ua`) вписується вигадане слово, яке більше ніде не
  зустрічається. Після імпорту перевіряється, чи знаходить його пошук.
  Негативний контроль (слово, якого немає в жодній картці) має давати 0.
  Код: `prom_marker_step.py`, `prom_marker_check.py`.

### 6.3. Epicentr

- Справжній API кабінету — core-api (SKILL-20). PIM API — для контенту,
  окремий XML — для наявності.
- Фільтр OMS `statusCode=new` API ігнорує, тому фільтрувати треба на своєму
  боці.
- «Валідне» можна казати лише за фактом: успішний імпорт, підтвердження
  менеджера або відповідь PIM API. Власна перевірка «виглядає валідно»
  доказом не є.
- Є статуси товару, які продавцю міняти не дозволено (SKILL-20).

## 7. Замовлення (наскрізний шлях)

Детально: `.claude/skills/skill-33-noire-order-end-to-end/SKILL.md`,
`SKILL-19-order-agents.md`, `SKILL-24-ttn-flow.md`,
`shared/knowledge_base/orders_playbook.md`.

```
1. Агент (systemd, кожні 5 хв) бачить нове замовлення майданчика
2. Перевіряє наявність у постачальника (три стани; без доказу НЕ скасовує)
3. Telegram власнику: товари, сума, оплата, доставка
4. ТТН Нової Пошти:        tools/np_create_ttn.py
5. ТТН у майданчик + статус 61, перевірка GET
6. Замовлення в CRM постачальника з ТТН і PDF-наклейкою: tools/smtm_crm.py
7. «До сплати» зафіксовано, лист-підтвердження CRM звірено
8. Telegram: підсумок
9. Наскрізна звірка:        tools/noire_order_verify.py (лише читання)
```

### 7.1. Агенти замовлень: правило доказу

- **Без доказу не скасовувати.** Відсутність товару в одному джерелі не є
  доказом, бо фіди відстають і мають різну семантику. Скасування незворотне
  й б'є по рейтингу магазину.
- Перед вмиканням агента для нового постачальника зробити два заміри
  (SKILL-16): як часто фід бреше про наявність і з якою затримкою
  оновлюється.

### 7.2. Нова Пошта (`tools/np_create_ttn.py`, API 2.0)

- `InternetDocument.save`: відправник, отримувач, `OptionsSeat` (у нас
  коробка 30×20×10), опис = **коротка назва товару** (бренд + модель,
  ≤40 символів, «+N» для кількох позицій), номер замовлення майданчика
  записується в ТТН.
- **Пастка:** після друку наклейки `InternetDocument.update` більше не працює
  («Document is already printed»). Друкувати лише остаточну ТТН.
- **Післяплата на картку** (`BackwardDeliveryData[].PaymentCard`) може бути
  заблокована на рівні договору: помилка `20000201794`. Інші назви полів
  картки API **мовчки ігнорує**, тому після створення завжди перевіряйте,
  що післяплата справді є в ТТН. Наш обхід: створити ТТН без післяплати й
  надіслати в Telegram нагадування «додайте післяплату N грн». Для
  нормальної роботи потрібен договір ФОП/юрособи з НП.
- Відстеження: `TrackingDocument.getStatusDocuments` з телефоном відправника.

### 7.3. CRM постачальника через браузер (`tools/smtm_crm.py`)

Метод, який можна перенести на **будь-яку** B2B-CRM постачальника без
публічного API:

1. **Вчитися по скріншотах власника.** Власник показує крок з позначками,
   агент повторює, і лише потім крок стає кодом. Незворотні кнопки
   («Оформити замовлення», оплата) натискає людина або агент **лише за її
   прямою вказівкою**.
2. **Безпечна розвідка.** У Playwright `ctx.route` блокує всі не-GET
   запити, поки вивчаєте сторінки. Так нічого не створиться випадково.
3. **Внутрішній API замість кліків.** React/MUI-форми не бачать
   `fill()`, потрібне введення з клавіатури. Надійніше знайти внутрішні
   ендпоінти (кошик, чекаут, прикріплення файлу) і викликати їх через
   `fetch` у контексті сторінки з тим самим заголовком авторизації, що й
   фронтенд (у SexOpt це `x-auth-token` з `localStorage`).
4. **Пастка кількості.** У SexOpt зміна поля кількості сама додає товар у
   кошик, тож натискання кнопки після неї дало 3 замість 2. Функція
   `add(sku, qty)` має виставляти **кінцеву** кількість, а не додавати.
5. **Пошук за артикулом через URL** і очікування лічильника «N з N
   товарів»: до фільтрації сторінка показує випадкові товари.
6. **Звірка з листом-підтвердженням.** Сума й **валюта** беруться з рядка
   замовлення (у нас USD, хоча кошик показував гривні). Помилку у валюті
   помітив власник, а не агент.
7. **Оплату постачальнику не автоматизовано** за рішенням власника. Це
   питання безпеки.

### 7.4. Наскрізна звірка (`tools/noire_order_verify.py`)

Лише читання: Rozetka ↔ НП ↔ CRM. Позначки ✅ / ⚠️ / ❌ / ℹ️, код виходу 1
при ❌, `--tg` надсилає звіт. Перевіряє: ТТН у майданчику = ТТН у НП =
ТТН у CRM; статус; склад замовлення = склад у CRM; номер документа
постачальника; оплату; «оплачено понад 24 год, але не відвантажено».

**Коли вмикати повну автоматику:** лише після 3 замовлень поспіль із 0 ❌,
серед яких є передоплачене й багатопозиційне, і з явного дозволу власника.
До того агент готує кожен крок, а людина підтверджує.

## 9. Правила роботи агента (найцінніше — переносити обов'язково)

### 9.1. Межі самостійних дій (SKILL-22, AGENT_RULES §1)

Без явного дозволу власника агент **не робить**:

- змін у працюючих агентах і сервісах, crontab, systemd, `.env`;
- видалення чи перезапису даних у БД (перед зміною — резервна копія в `backups/`);
- `git push --force` (виняток — узгоджений механізм публікації фід-репо);
- незворотних дій назовні: скасування замовлення, оформлення замовлення в
  CRM, оплата, відповідь менеджеру майданчика, лист у підтримку.

Облікові дані зберігаються **лише в `.env`**. Токени не виводяться в лог чи
чат. Дані покупців не потрапляють у git.

### 9.2. Дисципліна вимірювання (SKILL-21, SKILL-28, AGENT_RULES §11)

- **Позитивний контроль.** Перевірка, яка не здатна знайти дефект, нічого
  не доводить. Спершу переконатися, що на відомому випадку вона дає
  «знайдено». У нас контрольний запит двічі провалювався: спершу через
  застарілу назву у фіді, потім через мерехтіння видачі.
- **Негативний контроль.** Те, чого точно немає, має давати 0.
- **Різниця двох підрахунків — це список, а не число.** Відкрийте й
  подивіться на рядки. Нуль знахідок часто означає, що ви шукали в полі
  з іншою назвою (`feed_fields.py` показує реальні поля).
- **Ефект відбору.** Висновок з 10 товарів, «де ми вже бачили явище», на
  30 випадкових перевернувся («нарівні» → «удвічі гірше»). Для висновків
  брати **випадкову** вибірку з різних категорій, рахувати p-значення
  (`power_fisher.py`, `sample_bias_check.py`).
- **Повтори.** Живі системи (пошук, API) шумлять. Кожен замір щонайменше
  двічі, з контрольною групою (SKILL-28).
- **Позначки впевненості у звітах:** (В) виміряно, (Д) задокументовано
  майданчиком, (П) припущення. Припущення ніколи не подаються як факт.
- **Перевіряти записом-читанням.** Після кожного запису в API (ТТН, статус,
  ціна) робити окремий GET і звіряти.
- **Тест на собі, потім прибрати.** Експерименти, що міняють живі картки,
  робити на обмеженій кількості, з журналом і планом відкату.

| Пастка | Наслідок | Захист |

## 10. Розгортання з нуля (для колеги)

1. **Власні облікові записи:** GitHub (два репо: код і фіди; фід-репо має
   бути публічним, щоб працювали raw URL), кабінети майданчиків, API-токени,
   договір і API-ключ Нової Пошти, Telegram-бот (@BotFather) і chat id,
   Anthropic API key, сервер Linux.
2. **Код:** створити **новий** репозиторій, скопіювати код, видалити
   `data/*.xml`, `exports/`, `data/*` з нашими даними (розділ 1.2), усі `*.bak*`,
   `backups/`, `docs/*_2026*` (наші листи й заміри), `docs/work_journal.md`
   (почати свій).
3. **Заміни:** пройти список з розділу 1.3 і запустити `git grep` з 1.5.
   Ідентифікатори магазину краще винести в `.env` або `config`, щоб не
   шукати їх по файлах.
4. **Середовище:** `python3 -m venv venv && venv/bin/pip install -r requirements.txt`;
   для браузерних задач — `playwright install` і Camoufox (SKILL-03).
5. **`.env`** — з `.env.example`, лише власні значення. Назви змінних:
   - БД і сервіси: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`,
     `REDIS_*`, `QDRANT_*`, `OLLAMA_*`;
   - LLM: `ANTHROPIC_API_KEY`;
   - майданчики: `ROZETKA_LOGIN`, `ROZETKA_PASSWORD`, `ROZETKA_API_TOKEN`,
     `PROM_API_TOKEN`, `EPICENTR_TOKEN`, `EPICENTR_API_URL`;
   - Telegram: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_ID`, `TG_BOT_TOKEN`, `TG_CHAT_ID`;
   - НП: `NP_API_KEY`, `NP_COD_CARD`;
   - постачальники: `<SUPPLIER>_FEED_URL`, `<SUPPLIER>_LOGIN` / `_PASSWORD`;
   - інше: `SMTP_*`, `GITHUB_TOKEN` (лише на свій фід-репо);
   - прапорці: `NOIRE_PROM_IN_STOCK`, `NOIRE_AUTOCONFIRM` (у себе
     перейменувати; автопідтвердження вимкнене, доки не пройдено чекліст 7.4).
6. **БД:** `docker compose up -d postgres redis qdrant`. Схему створюють
   скрипти першого запуску: синхронізація постачальника, завантаження
   категорій (`rozetka_categories_fetch.py`, `epicentr_categories_fetch.py`,
   `prom_category_map_init.py`).
7. **Спершу вручну, потім у cron.** Кожен крок (синхронізація → генерація
   → валідація → публікація → звірка хешу) прогнати руками. Лише потім
   записати в crontab.
8. **Агенти замовлень** вмикати останніми, після замірів з 7.1 і з
   ручним підтвердженням кожного кроку.

## 11. Рецепт нового постачальника (зразок — dropoffice)

dropoffice (будматеріали, Rozetka) — найсвіжіший і найчистіший приклад.
Файли: `tools/dropoffice_rozetka_generator.py`, `tools/dropoffice_rozetka_audit.py`.

1. **Аналіз фіду:** `tools/feed_fields.py <src.xml> --params`. Скільки офферів,
   які поля, що з наявністю, що з ціною, чи є друга мова, фото з
   інфографікою.
2. **Конкуренти й категорії:** для 20–30 SKU знайти ці самі товари на
   майданчику (`rozetka_competitors.py`) і взяти категорії, де вони лежать.
3. **Довідник категорії:** параметри й одиниці з API майданчика в JSON
   (у нас `data/dropoffice_category_options.json`, формат можна взяти,
   значення — ні).
4. **Генератор:** назва → розміри (`name_dims_mm()`), параметри з одиницями
   (`with_unit()`), опис лише про одиницю (`unit_only_description()`),
   вирівнювання розмірів в описі під назву (`align_desc_sizes()`),
   фото з override/exclude, ціна з `price_rules`.
5. **Аудит «до/після»** за зауваженнями майданчика: рахувати і в
   джерелі, і в своєму фіді.
6. **Два шари валідації** → публікація через `publish_github()` → звірка хешу.
7. **Реєстр зауважень** модератора, відповідь менеджеру з цифрами.
8. **Журнал і скіл:** записати, що дізнались про постачальника (пам'ять
   агента, `shared/knowledge_base/supplier/`).
