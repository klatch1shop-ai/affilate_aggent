# ЗАВДАННЯ 01: розпізнавання голосових і текстових команд Telegram-бота

**Виконавець:** безкоштовна модель через `shared/utils/llm_router.py`.
**Приймає роботу:** основна модель за тестами `tests/test_voice_intents.py`.
**Дата постановки:** 16.09.2026.

---

## 1. Навіщо це

У бота (`tg_dispatcher/main.py`) голос уже перетворюється на текст
(faster-whisper), але далі текст потрапляє в примітивний розбір за словами:
шість `if` по підрядках, більшість гілок відповідає «в розробці».
Через це:

- «покажи замовлення за сьогодні» і «які замовлення» дають те саме, без дати;
- номер замовлення чи ТТН у фразі ігнорується повністю;
- «скільки SX2730 на складі» не розпізнається взагалі;
- порядок `if` вирішує все: у фразі «ціни на Розетці» спрацює гілка Prom,
  бо слово «ціни» перевіряється раніше за «розетка».

Потрібен окремий модуль розбору наміру, який можна перевірити тестами
без Telegram, без мережі й без LLM.

---

## 2. Що зробити

Створити **один файл** `tg_dispatcher/ai_brain/intents.py`.

### 2.1. Обов'язковий інтерфейс (не змінювати назви)

```python
def parse(text: str) -> dict
```

Повертає словник **рівно з такими ключами**:

| ключ | тип | зміст |
|---|---|---|
| `intent` | str | один з переліку в §2.2 |
| `params` | dict | знайдені параметри (§2.3), лише ті, що є у фразі |
| `mutating` | bool | чи змінює дія стан системи (у цій версії **завжди False**) |
| `confidence` | float | 0.0–1.0, див. §2.4 |
| `raw` | str | вхідний текст без змін |

### 2.2. Перелік намірів (рівно ці рядки)

| intent | коли | приклади фраз |
|---|---|---|
| `orders_new` | питають про нові/сьогоднішні замовлення | «які нові замовлення», «замовлення за сьогодні», «щось замовили?» |
| `order_status` | питають про конкретне замовлення | «що із замовленням 906209393», «статус замовлення 906078985» |
| `ttn_status` | питають про накладну | «де посилка 20451537526626», «статус ттн 20451537526626» |
| `stock` | питають наявність товару за артикулом | «скільки SX2730 на складі», «чи є SO3270» |
| `price_alerts` | питають про ціни й демпінг | «цінові алерти», «хто демпінгує», «перевір ціни» |
| `feed_status` | питають про фіди й публікації | «що з фідом розетки», «фіди оновились?», «публікація прому» |
| `system_status` | питають про стан системи, сервіси, агентів | «як справи», «статус системи», «сервіси живі?» |
| `help` | просять допомогу чи перелік команд | «що ти вмієш», «допомога», «команди» |
| `unknown` | нічого з переліку не підходить | «привіт», «яка погода» |

### 2.3. Параметри

| ключ | як розпізнати | приклад |
|---|---|---|
| `order_id` | 9 цифр поспіль | `906209393` |
| `ttn` | 14 цифр поспіль | `20451537526626` |
| `sku` | 2 латинські літери + 4–5 цифр, регістр не має значення, повертати ВЕЛИКИМИ | `sx2730` → `SX2730` |
| `marketplace` | «розетка/rozetka» → `rozetka`; «пром/prom» → `prom`; «єпіцентр/епіцентр/epicentr» → `epicentr` | `rozetka` |
| `period` | «сьогодні» → `today`; «вчора» → `yesterday`; «за тиждень/тиждень» → `week` | `today` |

**Важливо:** 14 цифр — це ТТН, а не замовлення. Перевіряти довший шаблон першим.

### 2.4. Впевненість

- `1.0` — у фразі є параметр, який однозначно визначає намір
  (номер замовлення, ТТН, артикул);
- `0.8` — збіг за ключовими словами наміру;
- `0.5` — збіг лише за одним загальним словом («ціни» без решти контексту);
- `0.0` — `unknown`.

### 2.5. Правила розбору

1. **Параметр сильніший за слова.** Є 14 цифр → `ttn_status`, навіть якщо у
   фразі є слово «замовлення». Є 9 цифр → `order_status`. Є артикул →
   `stock`, якщо поряд немає слів про ціну; зі словом «ціна» → `price_alerts`
   з параметром `sku`.
2. **Маркетплейс не визначає намір сам по собі.** «що з фідом розетки» —
   `feed_status` + `marketplace=rozetka`; «замовлення розетки» — `orders_new`
   + `marketplace=rozetka`.
3. **Порядок перевірок не може вирішувати результат** так, як зараз у
   `handle_text`. Спершу шукаються параметри, потім намір.
4. **Жодних звернень до мережі, LLM чи бази.** Тільки розбір рядка.
5. Регістр і зайві пробіли не впливають. Розділові знаки не заважають.
6. Українська й російська форми слів обробляються однаково
   («замовлення» і «заказ», «наявність» і «наличие»).

## 3. Обмеження

- **Тільки цей файл.** Нічого більше не створювати й не редагувати —
  `tg_dispatcher/main.py` не чіпати. Вбудовуванням займеться основна модель
  після перевірки.
- Стандартна бібліотека, без зовнішніх пакетів.
- Python 3.13.
- Файл має імпортуватись без побічних дій (ніякого коду на рівні модуля,
  крім констант і компіляції регулярних виразів).
- Коментарі й docstring — українською.

## 4. Як приймається робота

```bash
venv/bin/python -m pytest tests/test_voice_intents.py -q
```

**Умова приймання: усі тести зелені.** Тести написані замовником наперед і
не редагуються виконавцем. Якщо тест здається помилковим — це описується в
звіті, а не виправляється.

Додатково перевіряється:
- файл імпортується без помилок;
- `parse('')` не падає, повертає `unknown`;
- час розбору однієї фрази менший за 10 мс.

## 5. До чого це під'єднається потім (довідково, у цій задачі НЕ робити)

Власник 16.09: у боті робочого немає нічого — є лише **перевірені методи
API**. Модуль розбору саме для того, щоб кожен намір мав однозначний метод.
Виконавцю це потрібно тільки як пояснення, навіщо потрібні саме такі
параметри.

| intent | перевірений метод |
|---|---|
| `orders_new` | `rozetka_order_agent.get_orders_by_status()` / `get_new_orders()` |
| `order_status` | `rozetka_order_agent.get_order_details(order_id)` |
| `ttn_status` | НП `TrackingDocument.getStatusDocuments` (`tools/np_create_ttn.py`) |
| `stock` | `sexopt_products` у БД (`available`, `quantity`) |
| `price_alerts` | `tools/price_rules.py`, `noire_stock_sync.check_antidumping()` |
| `feed_status` | `tools/watchdog.py` — свіжість і доступність фідів |
| `system_status` | `systemctl --user is-active` + watchdog |

Наміри цієї версії **лише читають**. Тому `mutating` завжди `False`:
створення ТТН, зміна статусу й оформлення замовлень голосом не робимо,
поки шлях не відпрацює тричі поспіль без помилок.
