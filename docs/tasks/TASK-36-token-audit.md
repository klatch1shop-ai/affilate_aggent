# ЗАВДАННЯ 36 (дослідження): де наша система марнує контекст і токени

**Виконавець:** Codex. **Тип:** дослідження (скіл `worker-task-craft`, розділ «Завдання-дослідження»).
**Дата:** 21.09.2026. **Код не змінювати** — результат лише звіт
`docs/research/TOKEN_AUDIT.md`.

## Навіщо саме ти
Зовнішній консультант (Gemini) уже дав загальні поради — вони в
`docs/research/EFFICIENCY_CONSULT.md`. Слабке місце тих порад: модель **вигадувала**
стан нашої системи, бо не бачила коду. У тебе код є. Тому від тебе потрібні не поради,
а **виміряні факти з посиланнями `файл:рядок`**.

## Що зробити

### Частина А. Вимірювання (це головне)
1. **Виклики LLM.** Знайди всі місця, де код звертається до LLM (Gemini, Ollama,
   інші). Для кожного: файл:рядок, яка модель, чи заданий `max_tokens`/
   `maxOutputTokens`, чи задана `temperature`, чи вимагається JSON без обгортки.
   Окремо познач ті, де ліміт виходу **не заданий** — там модель може писати скільки хоче.
2. **Розмір системних інструкцій.** Виміряй у символах: наші скіли
   (`~/.claude/skills/*/SKILL.md` — лише якщо доступні; інакше пропусти й скажи чому),
   `AGENTS.md`, `CLAUDE.md`, найбільші файли в `docs/tasks/`. Назви 10 найбільших.
3. **Довгий вивід.** Знайди команди й функції, які повертають великий текст
   (тести, `git diff`, SQL-дампи, читання фідів). Для кожної — скільки приблизно
   рядків/символів вона віддає на типових даних. Де є обрізання, а де немає.
4. **Повторне читання.** Чи є в коді місця, де той самий файл або та сама вибірка
   читається кілька разів у межах одного прогону? Назви конкретні.
5. **Найбільші файли репозиторію** (топ-15 за розміром, без `venv/`, `.git/`,
   `output/`, `data/`) — щоб знати, що не можна читати цілком.

### Частина Б. Перевірка чужих тверджень
Власник зберіг поради зовнішньої моделі. Перевір **по нашому коду**, правда це для нас чи ні.
Для кожного — вердикт (`правда` / `неправда` / `не стосується нас`) і посилання `файл:рядок`.

1. «Агенти пересилають один одному історію думок, і на цьому горять токени».
2. «Потрібен спільний стан (`state.json` / Redis / Blackboard), бо агенти передають дані в промпті».
3. «Потрібен LangGraph або CrewAI для керування станом».
4. «Передавайте дифи, а не цілі файли — економія до 90 % вхідних токенів».
5. «Виставте `max_output_tokens: 150–300` для агентів».
6. «Потрібна векторна база (RAG) замість утримання логу сесії».
7. «Оркестратор має обрізати вивід команд до перших 3 і останніх 5 рядків».
8. «Гарячий системний промпт треба кешувати (Gemini Context Caching)».

### Частина В. Що з цього робити нам
Список конкретних змін **у нашому коді**, відсортований за співвідношенням
«ефект / складність». Для кожної: який файл змінювати, що саме, і **як виміряти**,
що стало краще. Не більше 7 пунктів. Якщо якась зміна суперечить нашим правилам
(нічого не публікувати без дозволу, не чіпати бойові скрипти в `tools/`) — сказати це.

## Правила дослідження
- **Кожне твердження — з посиланням** `файл:рядок` або з командою, якою ти це виміряв.
- Мережу не використовувати. Зовнішні джерела не потрібні.
- Якщо щось виміряти не вдалося — окремий розділ «Не перевірено і чому».
- Нічого не виправляти, навіть якщо бачиш помилку: тільки описати.
- Числа не округлювати «на око»: показуй команду, якою рахував.
