# SKILL-37: атрибути карток — три проходи, і жодного вигаданого значення

**Перевірено 20.09.2026** на косметиці SMTM для Епіцентру (67 нових карток, 15 з браком
обов'язкових атрибутів).

## 1. Порядок проходів (саме в такому)

| # | Прохід | Що робить | Віддача 20.09 |
|---|---|---|---|
| 1 | **З полів товару** | значення вже є в даних: країна з `country_of_origin`, об'єм/вага з габаритів, бренд із довідника | базові атрибути й так проставляє генератор |
| 2 | **Дослівний збіг із довідником** | значення довідника майданчика (`epicentr_attr_options`: `attr_code` + `cat_code` → `valuecode`) зустрічається в назві/описі; **рівно один** збіг — беремо | +3 значення |
| 3 | **Gemini з цитатою** | модель обирає **лише зі списку дозволених значень** і **зобов'язана навести цитату** з опису; без цитати або не зі списку — відкидаємо | +9 значень (аромат, смак, тип) |
| 4 | **Рішення власника** | те, чого в даних нема взагалі («Клас косметики», «Тип шкіри», «Призначення», «Стать») | 0 автоматично — **питати власника** |

**Результат першого підходу:** 12 значень, жодної повної картки.

### 1.1. Головна причина порожніх значень — не модель, а відсутній довідник

20.09: після першого підходу лишилось 56 незаповнених значень, і **для всіх** у нас не було
списку допустимих значень (`epicentr_attr_options` порожня для цих `attr_code` + `cat_code`).
Модель не може обрати зі списку, якого нема. Довантаження довідників з API
(`/v2/pim/attribute-sets/{set}/attributes/{attr}/options`, інструмент
`tools/epicentr_attrs_explorer.py::get_options`) дало 5 000+ значень — після цього:

| прохід | значень |
|---|---|
| дані + дослівний збіг | 12 |
| Gemini з цитатою | +40 |
| Gemini приблизно (дозвіл власника «заповнюй, навіть якщо неточно») | +26 |
| з назви (об'єм, тип упаковки — текстові атрибути без довідника) | +6 |
| **підсумок** | 54 з 67 карток без зауважень (решта — лише «одне фото») |

**Порядок перевірки, коли атрибут не заповнюється:** 1) чи є довідник значень у нас;
2) чи взагалі має довідник (текстові/числові атрибути — довідника нема, беремо з назви);
3) чи є підтвердження в даних; і лише потім — приблизне значення.

### 1.2. Два режими заповнення
- **Суворий** (за замовчуванням): лише з цитатою. Для карток, де помилка дорога (ціна, склад,
  сумісність, розмір).
- **Приблизний** (з дозволу власника): модель зобов'язана обрати зі списку найімовірніше або
  найзагальніше значення. Для «м'яких» атрибутів (стать, тип шкіри, клас косметики).
  Такі значення **позначати у звіті** — власник має знати, що вони здогадані.

## 2. Головні правила

1. **Ніколи не вигадувати.** Значення без підтвердження в даних — `НЕВІДОМО`. Модель, яку
   просять «заповнити картку», радо вигадає «Тип шкіри: для всіх типів» — і це потрапить у
   картку покупцеві (SKILL-23, `ollama-ukrainian-models`).
2. **Лише значення з довідника майданчика.** Вільний текст Епіцентр не приймає: потрібен
   `valuecode`. Тому в промпт іде список дозволених значень, а відповідь перевіряється на
   входження в нього.
3. **Цитата обов'язкова.** Без дослівного уривка з даних — значення не приймається.
   Це ловить «Країна-виробник: Іспанія», виведену з країни бренду, і «Стать: жіноча» з
   рекламної фрази «створено жінками для жінок».
4. **Не перезаписувати заповнені картки.** Епіцентр: повторний імпорт **стирає** характеристики
   карток у статусі «Наповнення контентом». Тому у файл ідуть **лише ті SKU, яких нема в кабінеті**
   (звірка через `core-api` `/v2/pim/products`, курсорна пагінація `cursor=`).
5. **Rozetka:** після подачі на модерацію зміст картки не змінюється (SKILL-36) — усе заповнювати
   ДО подачі.

## 3. Як це виглядає на практиці

```bash
# 1. свіжий список SKU кабінету (Епіцентр, лише читання)
#    POST core-api /v2/users/login → GET /v2/pim/products?limit=100&sort[]=-id&cursor=<next>
# 2. генерація фіду й відбір лише відсутніх у кабінеті
venv/bin/python tools/noire_epicentr_generator.py --output /tmp/full.xml
# 3. валідатор → перелік «чого бракує» по кожному SKU
venv/bin/python tools/noire_epicentr_validator.py <файл> > /tmp/v.log
# 4. проходи 2–3 (скрипти в scratchpad: cosm_det.py, cosm_enrich.py)
# 5. чисті картки — окремим файлом власнику; решта — список рішень
```

## 4. Що питати у власника (прохід 4)

Не «заповни за мене», а **готовий перелік** із варіантами: «Стать для масажних олій: унісекс?»,
«Клас косметики: мас-маркет?». Це бізнес-рішення, і воно однакове для цілої категорії — один
раз відповів, далі застосовується автоматично (зберігати в таблицю типових значень за категорією).

## 4.1. Фото — теж джерело фактів (20.09.2026)

Дані постачальника можуть суперечити упаковці: у назві SO3142 «190 г», на фото — «180 g / 6.3 oz».
**Gemini читає написи з фото** (`inline_data` + питання «випиши всі написи»), тож числові
характеристики (вага, обʼєм) звіряємо з упаковкою, перш ніж ставити в картку чи в сценарій ролика.
Розбіжність → не вгадувати, а питати постачальника й фіксувати в звіті.

## 4.2. Два незалежні джерела і хто перевіряє неточність (21.09.2026)

Питання власника: «хто буде ту неточність перевіряти». Відповідь — **не людина по всьому**,
а чотири фільтри, де людина дивиться лише те, що не пройшло машинні.

```
1. МАШИНА  значення мусить існувати в довіднику майданчика (valuecode) → інакше відкинуто
2. МАШИНА  дві НЕЗАЛЕЖНІ відповіді на ту саму характеристику:
             A = фото виробу   (що видно)
             B = опис постачальника (що написано)
3. ТРІАЖ   збіг A і B            → кандидат на запис
           лише одне джерело     → запис із позначкою джерела
           розбіжність           → ДО ВЛАСНИКА
           обидва «не знаю»      → лишається порожнім, не вигадуємо
4. ЛЮДИНА  усі розбіжності + випадкова вибірка (≈30) зі «збігів», щоб виміряти частку помилок
```

**Фото й опис — не дублі, а різні джерела.** Перевірено: фото дає те, що видно (колір,
текстура, форма), опис — те, що написано (кількість режимів, основа засобу). Тому справжніх
«збігів» мало, а більшість корисних випадків — «знає лише одне джерело». Це нормально й
саме тому обидва потрібні.

**Ризик залежить від характеристики, а не від моделі:**

| Характеристика | Фото | Опис | Кому вірити |
|---|---|---|---|
| Колір, текстура, форма, кількість у кадрі | ✅ надійно | часто мовчить | фото |
| Матеріал (силікон vs TPE vs ABS) | ❌ **на око не відрізнити** | ✅ якщо написано | лише опис |
| Кількість режимів, обʼєм, живлення | ❌ | ✅ | лише опис |
| Вага, обʼєм на упаковці | ✅ читає напис | ⚠️ може суперечити | фото (див. §4.1) |

**Пастка, на якій я вже наступив:** помилка транспорту — це **не відповідь**. У першому
прогоні `HTTP429` з обох джерел зараховувався як «ЗБІГ» і роздував точність. Будь-яку
відповідь, що починається з `HTTP`/`Error`, рахувати як **недійсний рядок**, а не результат.

**Ліміт, який визначає темп:** безкоштовний Gemini обмежений **кількістю запитів на добу**.
Одна характеристика = два запити (фото + опис). Тому 1 849 карток — це не «один прогін»,
а щоденні порції з обліком у `logs/llm_router.jsonl`.

## 4.3. Стани карток Епіцентру (перевірено в API, не здогад)

| Статус | Куди можна перейти | Права |
|---|---|---|
| `draft` | лише `new` | edit, delete, зміна категорії |
| `enrich` («наповнення контентом») | **`moderating`** | лише `product.edit`, `offer.edit` |

Тобто «відправити на модерацію» = перевести `enrich → moderating`, і **тільки після** того,
як не лишилось порожніх обовʼязкових. Перевірка порожніх: форма
`/v2/pim/products/forms/attribute-set/by-code/{set}/attributes` → `isRequired`,
звірка з `attributeValues` картки. Варіанти значень — `/v2/pim/attributes/{id}/options`
(за **id** атрибута з форми, не за `code`), посторінково.

## 4.4. Перенесення на Rozetka (коли дійдемо)

Метод не залежить від майданчика — змінюються лише три речі:
1. **звідки перелік обовʼязкових** (у Rozetka — `rozetka_category_params`, у нас уже є таблиця);
2. **довідник значень** (Rozetka теж не приймає вільний текст у select-полях);
3. **коли можна писати** — у Rozetka зміст картки після подачі на модерацію заморожений
   (SKILL-36), тож усе заповнювати **до** подачі, а не після, як в Епіцентрі.
Тріаж (§4.2) і правило «помилка ≠ відповідь» переносяться без змін.

## 5. Чого НЕ робити
- Не питати модель «заповни всі атрибути» без списку дозволених значень і без вимоги цитати.
- Не тягнути значення з назви бренду («США» ≠ країна виробництва).
- Не вантажити в кабінет картки з порожніми обов'язковими атрибутами «щоб потім заповнити
  вручну»: наступний повний імпорт зітре ручну роботу.
