## Повний ланцюг автоматизовано 04.10.2026

`tools/noire_order_pipeline.py` проходить усе: ТТН → наклейка → кошик →
оформлення → прикріплення ТТН → Telegram. Перевірено на справжньому
замовленні Rozetka 907753887 → постачальник **1421433**, ТТН
20451551736059, контроль оплати 1559 грн, до сплати 777.17.

### Будова сторінки ТТН (зчитана 04.10, точна)

```
input[1,2,3]  radio name=ttnOrigin
input[4]      text БЕЗ placeholder  ← поле «Номер ТТН»
input[5]      file, НЕВИДИМЕ        ← це норма, set_input_files працює
button        «Прикріпити», неактивна доки не заповнено обидва
```

Перше текстове поле на сторінці — пошук по каталогу
(`placeholder="Пошук по каталогу..."`), його брати НЕ МОЖНА. Правильний
селектор: `input[type=text]:not([placeholder])`.

### Три рівні страхування

1. **Не оформлювати двічі.** ID замовлення пишеться на диск ОДРАЗУ після
   натискання. Повторний запуск бере збережений і йде до ТТН. Без цього
   04.10 другий запуск створив би друге замовлення в постачальника.
2. **Збій прикріплення не мовчить.** Якщо ТТН не прикріпилась, власнику
   йде повідомлення з ID, номером ТТН, PDF і посиланням, щоб доробити
   руками.
3. **Будь-який збій ПІСЛЯ оформлення** → повідомлення власнику, бо
   замовлення вже існує й коштує грошей.

**Правду беремо з API постачальника**, а не з того, що здалося браузеру:
`ttnOrigin == 'TTN_FILE'`. Кнопка могла натиснутись без результату.

### Очищення кошика (перевірено 04.10 на живому залишку)

Нулювання кількості **не прибирає рядок**: `set_cart_qty(sku, 0)` лишає його
з `amount 0`, і кошик виглядає «не порожнім». Справжнє видалення — кнопка
**«Очистити всі корзини»** на `/uk/cart`.

`cart_is_empty()` рядки з нульовою кількістю за товар не рахує.

Порядок перевірок у конвеєрі має значення: спершу «чи вже оформлено», і лише
потім кошик. 04.10 було навпаки, і повторний запуск лишав товар висіти —
наступне замовлення стартувало б із чужою позицією.

Залишки прибираються САМІ з повідомленням власнику, а не блокують роботу.
Перевірено: у кошику лежав чужий SO5314, система прибрала його, поклала
SO7118 із замовлення, звірила склад, зупинилась.

`--check-only` проходить шлях нового замовлення до звірки кошика й
зупиняється ДО оформлення — для перевірок без зобовʼязань.

### Кошик один на акаунт — головний ризик паралельності

Два замовлення одночасно змішають позиції. Захист: замок на файлі, кошик
має бути ПОРОЖНІЙ на старті, склад кошика звіряється з замовленням ТОЧНО
(артикули й кількості) перед оформленням. Кілька позицій в одному
замовленні — одне ціле.

## Пастки (кожна траплялась 15.09)

1. **Поле кількості в картці саме додає товар у кошик.** Я вписав 2 і натиснув кнопку: вийшло **3 шт замість 2**. Тому `add` поле в картці не чіпає, а кількість ставить уже в кошику.
2. **`fill()` сайт на React не помічає.** 04.10 це вдруге зламало роботу —
   тепер уже ВХІД: кнопка submit лишалась неактивною 30 секунд, бо значення
   в полях форма не бачила. Пастка була записана для кошика, але не
   застосована до входу. Скрізь вводимо з клавіатури (`type(delay=)`). У полі видно значення, а запит іде зі старим (`amount: 1`). Пошук робимо прямою адресою, числа вводимо клавіатурою.
3. **Результати пошуку довантажуються.** Спершу там весь каталог («24 з 13985 товарів»), зокрема чужі «Маркетинговий матеріал» по 1 грн. Без очікування лічильника в кошик потрапить не той товар.
4. **Артикул є і в лівій панелі фільтрів.** Пошук за текстом артикула знаходить заголовок фільтра, а не картку.
5. **Без `x-auth-token` API віддає HTML.** Токен у `localStorage['token']` після входу. Перехоплення відповідей сторінки виявилось ненадійним: кошик читався то як 2 шт, то як порожній.
6. **Після кожної дії звіряємо `/inner/cart`.** Лічильник у шапці й поле на екрані — не доказ.

## Що є в кошику для наступного кроку

Поля кошика з `/inner/cart`:
- `ttnNumber`, `ttnOrigin`, `waitForTtn`, `ttnDate`;
- `payOnDeliverySum`, `deliveryPayer`, `deliveryServiceType`;
- `dsService`, `dsCity`, `dsPoint`, `dsRecipientName`, `dsRecipientPhone`;
- `comment`, `agreement`.

**Валюта (помилка 15.09):** `agreement` кошика (EUR) — **не** валюта товару. Рядок замовлення 1393615 має договір **USD**: SX2730 7,08 $ × 2 = **14,16 $**, а 637,20 грн — це за курсом 45,00, дійсним 1 робочий день. Вчорашнє 1392013 було в EUR (27,95 € = 1 458,99 грн за курсом 52,20). Суму до сплати беремо з «Історії замовлень» («Разом: …$/€») і звіряємо з листом («Усього: … UAH»).

Отже, при оформленні вказуються ТТН, післяплата й дані доставки. Кнопка на сторінці кошика — «Оформити».

## Безпечне дослідження сторінок

Нові сторінки CRM відкриваємо з блокуванням усіх запитів, крім GET
(`ctx.route` → `abort`). Дозволяємо поштучно лише той запит, про який уже
відомо, що він нічого не створює. Так 15.09 з'ясувалось, що «Оформити» спершу
шле `checkout/check`, і лише після цього сторінка оформлення відкривається.

## Межі

- Дані для входу лише в `.env` (`SMTM_URL`, `SMTM_LOGIN`, `SMTM_PASSWORD`). Сесія лежить у `~/.smtm/state.json` (поза git, 600). Токен сесії не друкувати.
- **«Оформити» лише за прямою вказівкою власника на конкретне замовлення.** Це реальне замовлення з оплатою з передоплати.
- Кошик спільний з кабінетом власника. Перед діями читаємо, що в ньому вже є.
- Метод повторення: власник показує крок на знімку, я повторюю, результат перевіряю через API. Новий крок записується сюди, лише коли його перевірено.
