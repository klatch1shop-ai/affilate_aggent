# SKILL-17: Єдиний конвеєр майданчика

Спільна процедура для Rozetka, Prom, Epicentr і будь-якого наступного
майданчика чи постачальника. SKILL-16 відповідає на питання «як підключити
постачальника», цей файл — «як влаштована робота з майданчиком після
підключення і чому саме так».

Головна теза, за яку заплачено найдорожче: **різниця між майданчиками — у
полях і лімітах, а не в процесі.** Процес однаковий, і кожен його гейт
зʼявився після конкретної аварії.

---

## 1. Інваріант конвеєра

```
джерело постачальника
   → нормалізація (одна база, одні назви полів)
      → мапінг категорій і характеристик
         → збірка фіду (генератор майданчика)
            → валідація (гейти нижче)
               → публікація
                  → ДОКАЗ публікації
                     → зворотний зв'язок модератора → реєстр
```

Дві останні ланки — не формальність. Без «доказу» ми вже надсилали менеджеру
посилання на невиправлений файл. Без «реєстру» два зауваження пролежали
місяць у стані «проаналізовано».

---

## 2. Гейти, які не можна пропускати

| Гейт | Де описаний | Що ловить |
|---|---|---|
| Правило «готово» | `CLAUDE.md` | локально виправлено, на сервері старий код |
| Позитивний контроль | `CLAUDE.md` | перевірка, яка не здатна знайти дефект |
| Симетрія парних гілок | цей файл, §4 | одна мова заповнена, друга ні |
| Походження даних | SKILL-14.8 | характеристика, взята з чужої картки |
| Реєстр зауважень | `tools/moderator_findings.py` | «проаналізовано» видане за «виправлено» |

**Порядок доповіді власнику.** Називати можна лише те, що має статус
`published` або `confirmed`. Усе інше — борг, і він озвучується окремим
рядком, а не ховається у формулюванні «працюємо над цим».

---

## 3. Матриця відмінностей майданчиків

Заповнюється фактами, перевіреними на практиці, а не документацією.

| | Rozetka | Prom | Epicentr |
|---|---|---|---|
| Опис | лише `description_ua` | `description` + `description_ua` | PIM API |
| Назва | `name` + `name_ua` (однакові) | `name` рос., `name_ua` укр. | PIM API |
| Пошукові запити | немає | `keywords` + `keywords_ua`, ≤1024 симв. | немає |
| Ліміт назви | за зразком категорії | 110 символів | — |
| Складені значення | окремий тег на складову | розділювач `\|` | — |
| Заморозка картки | від моменту відправки на перевірку | немає | партіями |
| Публікація | XML на GitHub → URL | XML на GitHub → URL | PIM API |
| Модерація | відділ адаптації, листи | автоматична + ProSale | менеджер |

**Перед будь-якою перевіркою фіду** — інвентаризація реальних полів:

```bash
python3 tools/feed_fields.py output/<feed>.xml --params
```

Саме тут видно, що описи Rozetka живуть у `description_ua`, а `Об'єм`
записаний із апострофом U+0027. Запит із чужою назвою поля дає нуль
знахідок і виглядає як добра новина.

---

## 4. Симетрія парних гілок

Скрізь, де є дві паралельні гілки — дві мови, два фіди, два джерела, —
міряти обидві **після кожного кроку** й порівнювати числа.

Три випадки за один день, кожен виглядав як брак даних, а був дефектом коду:

* keywords писались лише в російське поле — українське вважалось неіснуючим;
* російські фрази різались на `[:5]`, українські на `[:8]`;
* збір російських тегів дав 0 фраз (regex вимагав префікс `/ru/`), а після
  «виправлення» приніс 105 українських фраз під міткою «російські» — Prom
  тримає мову в сесійних куках.

Практичний висновок для скрейперів: **свіжий контекст браузера на кожну
мову й на кожен запит**, і перевірка, що отримане справді тією мовою, яку
просили (українські літери `іїєґ` у російському полі — помилка).

## 5. Якість контенту: спільні інструменти

| Задача | Інструмент | Придатний для |
|---|---|---|
| Інвентаризація полів фіду | `tools/feed_fields.py` | усі |
| Оцінка 0-100 | `tools/noire_feed_scorer.py` | Prom, розширюваний |
| Аудит фото: дублі, коди, обрізка | `tools/noire_photo_audit.py` | усі |
| Реєстр зауважень модератора | `tools/moderator_findings.py` | усі |
| Пошукові запити | `tools/prom_keywords.py`, `prom_tag_harvest.py` | Prom |
| Перевірка видимості у видачі | `tools/prom_visibility_check.py` | Prom |

**Про фото.** Три різні зауваження Rozetka — QR-коди, асортимент у картці,
дублікати кадрів — мають одне джерело: скан упаковки постачальника. На ньому
одночасно QR і штрихкод, усі кольори лінійки в одному кадрі й той самий
файл під двома URL. Тому маркер «на зображенні є код» закриває три пункти
одразу, а порівняння URL не закриває жодного: точних дублів у фіді нуль,
дублі перцептивні.

Що цей маркер **не** ловить: маркетингове фото розсипу саше й невідповідність
кольору на кадрі. Це вміст зображення, тут потрібна модель із баченням або
очний перегляд списку.

## 5а. Маркер «спільне зображення» — асортимент без розпізнавання картинок

Перевірений метод, який закрив три зауваження Rozetka без моделі з баченням.

**Ідея.** Якщо одне й те саме зображення (однаковий перцептивний хеш) стоїть
у картках із **різним** значенням характеристики, воно не може бути
правдивим для всіх. Це знімок лінійки, а не товару.

**Головне — правильно обрати характеристику.** Перевірено на живих даних:

| Характеристика | Карток | Висновок |
|---|---|---|
| Розмір | 15 313 | **не конфлікт.** Сукня S і L на фото однакові |
| Обʼєм | 178 | **конфлікт, видаляти.** Кадр pjur із пʼятьма пляшками |
| Колір | 1862 | **конфлікт, але лише зсувати** |

Різниця між «видаляти» і «зсувати» зʼявилась після очного перегляду
вибірки, і без неї метод зробив би шкоду. Найбільші групи кольорових
конфліктів виявились **розмірними сітками бренду** (Passion, Noir Handmade),
спільними для всієї лінійки: видалити їх означало б прибрати корисну
інформацію з 1862 карток. Але головним кадром вони бути не можуть — як і
фото червоних трусиків у картці «Золотий» (SO5189).

Тому правило: **спільне зображення не видаляємо, а забороняємо ставити
першим**. Це заразом закриває вимогу «товар на перших фото має бути видно
повністю» без жодної евристики про вміст кадру.

Побічний продукт, вартий окремої уваги: 11 карток, де **всі** фото спільні —
постачальник не дав жодного знімка саме цього кольору
(`docs/rozetka_need_own_photos.csv`). Це запит до постачальника, а не
дефект фіду.

**Чого маркер не ловить:** маркетингове фото розсипу саше, невідповідність
кольору в картці, де фото унікальне. Це вміст зображення.

## 5б. Характеристики: довідник майданчика замість карток конкурентів

SKILL-09 радить дивитись живі картки конкурентів. Для Rozetka знайшлось
точніше джерело — **звіт по категорії з кабінету продавця** (у нас
`category_report_<rz_id>.xls`). Він дає не здогадку, а повний перелік
параметрів із трьома критичними колонками:

* **Тип фільтра** — `main` проти `disable`. У Лубрикантах із 25 параметрів
  у фільтри потрапляють лише **шість**. Решта — «Гарантія», «Код УКТ ЗЕД»,
  «Кнопка передзамовлення» — покупець у фільтрі не бачить, і заповнювати їх
  заради зауваження «додайте характеристик» безглуздо. Це звузило роботу
  вчетверо.
* **Тип параметра** — `List` проти `ComboBox`, тобто чи можна кілька
  значень. Кожне значення `List` виводиться **окремим тегом** `<param>`.
* **Перелік дозволених значень** — джерело істини для витягу з тексту.

Порядок: спершу отримати звіт, потім рахувати розрив, і лише потім писати
правила. Зворотний порядок означає роботу над полями, яких ніхто не бачить.

**Витяг значень із тексту** (`tools/rozetka_lube_params.py`) — лише з назви
й опису самого товару, лише зі списку дозволених значень, ніякого
домислювання. Дало 4.6 → 6.3 характеристики на картку.

Дві пастки, на яких я вже спіткнувся:

* **Підрядок замість цілого слова.** «мед» знайшовся в «медичний»,
  «медицині», «камедь» — 40 хибних ароматів. Потрібен пошук цілого слова, і
  довжина допустимого закінчення має залежати від кореня: короткий («мед»)
  суворий, довгий («охолод») мусить прийняти «охолоджуючий».
* **Роздільник складених значень.** `|` не входив у розбиття, і 177
  заповнених характеристик мовчки не доходили до фіду.

## 5в. Офіційний валідатор — і чому він ловить те, чого не ловимо ми

Валідатор Rozetka **не потребує входу в кабінет**: посилання на фід, email
і капча (`sellerhelp/p178-pricevalidate`). Звіт приходить листом від
`gomer_services@rozetka.com.ua`, а детальний звіт відкривається за хешем із
листа **без авторизації** — тобто читати й розбирати його можна повністю
автоматично. Ручний лише крок із капчею.

У звіті є вигрузка XLSX із переліком проблемних позицій — беріть її, а не
переказ: там точні формулювання й точні SKU.

**Приклад, заради якого цей розділ існує.** 15.08.2026 перший же прогін дав
1403 попередження: 1226 «Дубль параметра з іменем "Розмір"» і 177 те саме
для «Призначення». Причина — виконана буквально вказівка менеджера
(«вказуйте два значення в параметрі Розмір»), реалізована двома окремими
тегами `<param name="Розмір">`. Наш валідатор це пропускав, бо два теги з
однаковим іменем — коректний XML.

Правильний синтаксис описаний у p185 і легко пропускається:
**багатозначний параметр — ОДИН тег, значення через `<br>` усередині
CDATA**:

```xml
<param name="Розмір"><![CDATA[L <br> XL]]></param>
```

Вимога менеджера при цьому виконана — значень справді два.

Мораль ширша за один тег: **слова менеджера кажуть ЩО показати, специфікація
каже ЯК це записати**. Виконання першого без другого дає фід, який менеджер
схвалив на словах, а система рахує проблемним. Тому обидві перевірки
обовʼязкові й жодна не замінює іншу.

Ще один орієнтир зі звіту: попередження не роблять файл невалідним
(«помилок 0, файл валідний»), але зменшують кількість **валідних товарів** —
у нас із 4147 до 2744. Тобто попередження — це не косметика.

## 6. Скорер як спільна метрика

Скорер має міряти те, що впливає на продажі, і не має саджати бал за те,
чого фізично немає в даних постачальника.

Два правила, виведені з практики:

* **Оцінкові значення рахуються як заповнене поле.** Постачальник не дає
  точної ваги, габаритів і діаметра по всьому каталогу — це підтверджено на
  Epicentr. Реалістична стеля — 100% заповнених полів (точних чи оцінкових),
  а не 100% точних даних постачальника.
* **Метрика мусить бачити не лише кількість, а й придатність.** Скорер
  показував ті самі 76.8 бала до й після виправлення мови keywords, бо
  рахував кількість фраз. Кожна нова вага має відповідати на питання: який
  дефект вона зробить видимим?

## 7. Чекліст на кожну ітерацію

1. `feed_fields.py` — які поля насправді є.
2. Позитивний контроль для кожної нової перевірки.
3. Зміни в генераторі; статистика змін у лог, не мовчки.
4. Порівняння «до/після» на рівні даних, не лише лічильників.
5. Деплой на сервер публікації + збіг MD5 генератора.
6. Публікація + git blob sha1 + завантаження URL.
7. `moderator_findings.py --status <id> published --note "<хеш>"`.
8. Доповідь: окремо зроблене, окремо борг.
