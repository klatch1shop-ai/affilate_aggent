# SKILL-24: ТТН — від накладної постачальника до статусу в кабінеті

> Коли потрібен: робота з накладними, обробка замовлень Rozetka, масштабування
> на нових постачальників чи майданчики.
> Аудит 31.08.2026: 23 замовлення з ТТН, 22 відвантажені, повторів нуль.

---

## Ланцюжок

Постачальник (Carvol) надсилає **PDF накладної в Telegram**. Далі автоматично:

| # | Крок | Де |
|---|---|---|
| 1 | парсинг PDF: номер ТТН, телефон, отримувач, місто | `agents/orders/ttn_pdf_parser.py` |
| 2 | уточнення в API Нової Пошти | `agents/orders/np_api.py` → `get_ttn_info` |
| 3 | зіставлення із замовленням | `match_order_by_np_data`, відкат на `match_order_by_ttn_data` |
| 4 | запис ТТН + статус | `rozetka_order_agent.set_ttn` → `change_status(3)` |
| 5 | **верифікація окремим GET** | `get_order_details` → звірка поля `ttn` |

Оркеструє `tg_dispatcher/main.py` (обробник документів).

### Виклики Rozetka

```
POST /orders/add-ttn  {"order_id", "ttn", "delivery_service_id": 1}   ← основний
PATCH /orders/{id}    {"ttn": ttn}                                    ← відкат
```

Після успіху статус сам стає **61** («ТТН додано»); далі `change_status(3)`.

## Що тут зроблено правильно — і чому це варто копіювати

**Система не вірить власній відповіді про успіх.** Крок 5 перечитує замовлення
окремим `GET` і звіряє поле `ttn`. Якщо `set_ttn` повернув успіх, а поле
порожнє — бот кричить «ALARM», а не рапортує «готово».

Це той самий позитивний контроль, що й у SKILL-21: **код відповіді 200 — це
факт про запит, а не про стан системи.**

**Два джерела даних із явним пріоритетом.** Спершу API Нової Пошти (авторитетне
джерело), при невдачі — дані з PDF. У повідомленні завжди видно, яке джерело
спрацювало: `[НП API]` чи `[PDF (fallback)]`. Помилка не ховається.

**Неоднозначність не вирішується сама.** Якщо збігів кілька — бот показує
перелік із відсотками й **просить людину**: `/ttn ORDER_ID НОМЕР`. Автоматично
береться лише єдиний збіг.

## Стани замовлень Rozetka

`1 Нове → 2 Підтверджено продавцем → 61 ТТН додано → 3 Передано в доставку`
Окремо: `26 Обробляється менеджером`, `55 Скасовано`.

Агент опитує статуси **1, 2, 4, 26, 55, 61** (`types=4` — теж «нові»).
Параметр `types=all` повертає **порожньо** — не використовувати.

## Пропущений випадок, знайдений аудитом 31.08.2026

Замовлення з **безготівковою оплатою** (`payment_type: no_cash`) створюється
одразу в статусі **26 «Обробляється менеджером»**, а не «Нове». Агент цей
статус **бачить**, але обробляє тільки нові: підтвердити → Excel → Telegram
постачальнику. Тому таке замовлення **не доходить до постачальника** і
взагалі не потрапляє в `rozetka_processed_orders`.

Приклад: `#904651025`, створене 30.08, зависло без ТТН і без запису в БД.

**Це не збій, а відсутній сценарій.** Розширювати його треба обережно: там
передоплата й гроші, тож правильна поведінка — сповістити власника, а не
слати постачальнику автоматично.

## Що міряти при масштабуванні

| Замір | Норма | Тривога |
|---|---|---|
| дублікати ТТН | 0 | будь-який — накладну зарахували двічі |
| дублікати замовлень у БД | 0 | будь-який |
| `accepted` без ТТН | одиниці | 33 при 22 відвантажених (31.08) — половина без накладної |
| замовлення поза відомими статусами | 0 | новий статус = новий пропущений сценарій |

Запит для звірки — `rozetka_processed_orders`: колонки
`order_id, status, total_price, processed_at, phone, recipient, city, ttn`.
Поля `created_at` там **немає** (є `processed_at`).

## Слабке місце всієї схеми

Усе тримається на Telegram. Якщо `tg_dispatcher` не працює, накладні просто
не обробляються, і дізнаємось ми про це **з підвислих замовлень**, а не одразу.
Сторож `watchdog.py` стежить за процесом `tg-dispatcher`, але не за тим, чи
доходять накладні.
