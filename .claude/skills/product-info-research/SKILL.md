# Product Info Research — покрокові інструкції

Метод пошуку й перевірки відсутньої товарної інформації (країна виробництва,
матеріал, точні характеристики) для товарів, яких немає в основному фіді
постачальника. Перевірено на 1182 SKU NOIRE/SexOpt без `country_of_origin`
(липень 2026) — закрито 142 точним збігом, метод стабільний і повторюваний.

Не вигадувати і не ставити fallback-значення навмання — застосовувати лише
дані з явного структурованого поля джерела, при точному збігу моделі/артикулу.

---

## SKILL-01: Коли застосовувати цей метод

Використовувати щоразу, коли:
- в основному фіді постачальника відсутнє обов'язкове поле для маркетплейсу
  (`country_of_origin`, матеріал, точні розміри тощо)
- потрібно ЩЕ до листа постачальнику спробувати закрити частину списку
  самостійно — постачальник відповідає повільно ("з часом"), а частину даних
  можна дістати з відкритих B2B-каталогів того ж рівня гурту

Не використовувати для:
- підтвердження даних, які вже є в фіді (тільки для того, чого немає)
- масового перенесення значення з одного SKU бренду на весь асортимент бренду
  (див. SKILL-04 нижче — це заборонено окремим правилом)

## SKILL-02: Чому звичайний requests/BeautifulSoup не працює

Три класи блокерів:

1. **Антибот-захист.** Amazon `/dp/*` — HTTP 500 на будь-який прямий запит,
   незалежно від конкретної сторінки. EDC Wholesale — HTTP 403 на головну,
   ще до будь-якого логіну.
2. **JS-рендеринг без SSR.** EasyToys.nl — HTML категорії віддається, але
   список товарів і специфікації генеруються клієнтським JavaScript; у
   сирій відповіді сервера їх немає взагалі.
3. **Логін-стіна.** Williams Trading — прямий текст "please log in or
   create an account". Це організаційний бар'єр, не технічний — не
   намагатись обходити.

Класи 1 і 2 вирішує один інструмент — **Camoufox**. Клас 3 не вирішується
без реєстрації гуртового акаунту вручну.

## SKILL-03: Встановлення Camoufox (одноразово на сервері)

```bash
cd /home/tekken/agent-system
./venv/bin/pip install "camoufox[geoip]"
./venv/bin/camoufox fetch
```

> ⚠️ Завантажує ~660 МБ браузера в `~/.cache/camoufox/`. Перевірити
> встановлену версію: `./venv/bin/camoufox active` (прапорця `--version`
> немає; доступні команди — `active`, `fetch`, `list`, `path`). Це
> Firefox-форк з антидетект-патчами на рівні C++ (не JS-injection, який

> `--break-system-packages` — цей прапорець потрібен лише для системного
> Python, у venv він зайвий і збиває оточення.

## SKILL-04: Правила застосування знайдених даних

### Крок 1 — точний збіг моделі, не тільки бренду

Шукати конкретний артикул/назву моделі, не просто "цей бренд є в каталозі".
Приклад провалу: Orgie Dual Vibe Strawberry G&T знайдено на EasyToys, але
смак не вказано в картці — товар НЕ застосовано, бо неможливо підтвердити
що це саме той SKU.

### Крок 2 — структуроване поле, не маркетинговий текст

Приймати тільки окреме структуроване поле в специфікації товару:
`Herkomst`, `Country of Origin`, `Made in`. НЕ приймати:
`"British brand"`, `"founded in Japan"`, `"Swedish design"` — це не доказ
країни виробництва, лише країни реєстрації/дизайну бренду.

### Крок 3 — заборона переносу з бренду на всі SKU

> ⚠️ Критичне правило, підтверджене на практиці двічі:
> - Doc Johnson маркетингово "made in North Hollywood, USA" (>75% асортименту),
>   але конкретна модель Crystal Jellies Jr. Double Dong реально вироблена
>   в Мексиці.
> - Rocks Off виробляє одночасно у Великобританії, Європі й Китаї —
>   на рівні бренду країну взагалі неможливо визначити.
>
> Ніколи не застосовувати знайдену країну одного SKU бренду до інших SKU
> того ж бренду, навіть за відсутності протилежних доказів.

### Крок 4 — не довіряти vendor-полю постачальника сліпо

Виявлений випадок: SexOpt заявляє Zalo як США, тоді як виробничий підрозділ
бренду зареєстрований у Сучжоу, Китай (за даними B2B-каталогу
виробників — не офіційний реєстр, тому як доказ країни для конкретного SKU
це НЕ приймається). Vendor-поле постачальника може бути прямо помилковим —
це додатковий аргумент проти автопідстановки країни бренду замість країни
виробництва.

## SKILL-06: Порядок роботи

```bash
# 1. Список SKU з відсутнім полем
psql -h 192.168.3.28 -U agentadmin -d agentdb -c \
  "SELECT sku, name, vendor FROM sexopt_products WHERE country IS NULL OR country=''"

# 2. Скрейп з чекпойнтами
#    Продовження з місця зупинки — АВТОМАТИЧНЕ: SKU, вже наявні в
#    sexopt_country_lookup, пропускаються. Окремого прапорця --resume немає.
#    Доступні прапорці: --limit N (обмежити партію), --skus A,B,C (точковий прогін)
./venv/bin/python tools/noire_country_scraper.py

# 3. Перевірка типів збігу перед застосуванням
psql -c "SELECT match_type, COUNT(*) FROM sexopt_country_lookup GROUP BY match_type"
# exact    → застосувати
# partial  → НЕ застосовувати, лишити для постачальника
# notfound → НЕ застосовувати
# none     → НЕ застосовувати (знайдене — не той товар)
```

Орієнтир за часом: ~6 с на SKU, повний прогін 1182 SKU — 2 год 07 хв.

> ⚠️ Записувати результат завжди з джерелом (`source='easytoys'`, URL картки
> товару, оригінальна назва з картки і список незбіглих токенів у
> `sexopt_country_lookup`). Ніколи не перезаписувати поле мовчки — має
> залишатись слід, звідки взялось значення, для майбутньої ручної перевірки.

> ⚠️ Генератор бере з таблиці ЛИШЕ `match_type='exact'`
> (`load_country_lookup()` у `noire_epicentr_generator.py`). Значення в полі
> `herkomst` — нідерландською, переклад на назви довідника Єпіцентру робить
> `COUNTRY_ALIASES` у тому ж файлі.

## SKILL-07: Що НЕ робити

- Не переносити значення з однієї моделі бренду на весь асортимент бренду
- Не приймати маркетинговий текст як підтвердження країни виробництва
- Не обходити логін-стіну (Williams Trading) — це не технічна задача
- Не витрачати повторні спроби на `amazon.com/*/dp/*` прямими запитами —
  підтверджено HTTP 500
- Не застосовувати `partial`/`notfound`/`none` збіги навіть якщо дуже
  хочеться підняти відсоток покриття

## SKILL-08: Застосовність поза country_of_origin

Той самий метод (Camoufox + гуртові B2B-вітрини з розкритими specs)
підходить для будь-яких структурованих характеристик, відсутніх в
основному фіді постачальника — матеріал, точна довжина/діаметр, вага,
тип живлення. Логіка та сама: шукати структуроване поле специфікації,
не маркетинговий опис, застосовувати лише при точному збігу моделі.

## SKILL-09: Перевірка категорії за частиною назви на самому Epicentr

Окремий метод для іншого класу питань. SKILL-04..08 відповідають на «яка
характеристика в цього товару» і потребують точного збігу артикулу.
Тут питання інше — **«у якій категорії такий товар має лежати»**, і для
нього точний збіг не потрібен: достатньо знайти будь-який товар того ж
типу в конкурентів на самому маркетплейсі.

### Крок 1 — пошук за типом товару, не за моделлю

Шукати родове слово, бренд або характерну фразу: `презервативи`, `мило`,
`свічка`, `менструальна чаша`. Модель, розмір і колір значення не мають.

```bash
# adult.epicentrk.ua, пошук через Camoufox (звичайний requests не рендерить видачу)
https://adult.epicentrk.ua/ua/search/?q=<urlencoded>
```

> ⚠️ Обов'язково пройти віковий шлюз: кнопка «ТАК, ВИПОВНИЛОСЯ». Без цього
> видача порожня. Далі `wait_until='networkidle'` плюс пауза 6 с і прокрутка —
> результати домальовуються клієнтським JS.

### Крок 2 — читати SECTION_ID у фасетах видачі

Головна цінність сторінки пошуку — посилання-фільтри виду
`/ua/search/?q=<запит>&SECTION_ID=9460`. **`SECTION_ID` — це і є код
epicentr-категорії**, у якій лежать знайдені товари. Це пряма відповідь на
питання про категорію, без здогадок.

### Крок 3 — картка конкурента показує реальний набір атрибутів

На картці товару видно, які атрибути конкурент заповнив насправді. Приклад
(мило ручної роботи, 9460): `Бренд = Інше`, `Тип товару = мило`,
`Країна реєстрації бренду = Україна`, `Вага 0.36`. Атрибута `Матеріал` на
картці немає взагалі, хоча в наборі він значиться обов'язковим.

Це дає дві речі: підтвердження категорії та орієнтир, які значення
атрибутів реально проходять модерацію.

### Крок 4 — порожня видача теж є відповіддю

`На сайті "<запит>" не знайдено` означає, що маркетплейс цю товарну групу
не продає взагалі. Тоді питання не в тому, куди її покласти, а в тому, чи
є сенс її заводити — і це вже питання до категорійного менеджера.

### Перевірені результати (NOIRE/SexOpt, липень 2026)

| Запит | Результат | Висновок |
|---|---|---|
| `презервативи` | не знайдено | Категорії презервативів немає в жодному з 38 розділів інтимного дерева. 168 SKU лишено в 9526 як найменш хибному домі |
| `мило` | знайдено, `SECTION_ID=9460` | Мило-сувеніри лежать у «Еротичні приколи та сувеніри» — наш маппінг збігається з конкурентами |
| `свічка` | не знайдено | Свічок немає на вітрині взагалі, хоча категорія 9630 існує. Прецеденту для наших 42 свічок-сувенірів немає |
| `менструальна чаша` | не знайдено | Підтверджує, що доречної категорії немає; 9526 лишається вимушеним рішенням |

### Коли застосовувати

- Спірні випадки категоризації, де внутрішня логіка дає кілька варіантів
- Перед тим, як міняти маппінг цілої категорії постачальника
- Коли валідатор вимагає атрибут, для якого немає правдивого значення —
  подивитись, що в цій ситуації роблять конкуренти

> ⚠️ Відповідь конкурента — це не автоматично правильна відповідь. Це
> прецедент, який показує, що така категоризація проходить модерацію.
> Якщо вона суперечить здоровому глузду, рішення все одно за менеджером.

## SKILL-10: Верифікація ФОРМАТУ картки через живі приклади конкурентів

SKILL-09 відповідає на питання «у якій категорії має лежати товар».
Цей розділ — про інше питання, яке виникає постійно й окремо: **«як саме
має виглядати картка»**. Порядок слів у назві, які характеристики очікує
майданчик, як подавати складені значення, чи ставити артикул і де.

> Метод виріс із реального випадку: відділ адаптації Rozetka повернув фід
> NOIRE із сімома зауваженнями, серед них «порядок у назві має бути
> Тип - Виробник - Модель - Розмір - Колір - Артикул у дужках». Формулювання
> зрозуміле, але з нього не видно ні того, як писати складений розмір, ні
> чи потрібні пробіли в дужках. Відповідь знайшлася за три хвилини в
> публічному каталозі самої Rozetka.

### Крок 1 — не вигадувати і не питати людину першою

Порядок дій саме такий:

1. знайти **живі, вже опубліковані** картки того самого типу товару
   в тій самій категорії того самого майданчика;
2. зняти з них структуру;
3. і лише якщо це не дало відповіді — ескалювати до людини **зі звуженим
   питанням**, а не з нуля.

Питати менеджера про те, що видно у відкритому каталозі, — марна витрата
чужого часу й власного циклу очікування (відповідь іде днями).

### Крок 2 — де шукати

- **Прямий перегляд категорії маркетплейсу** — найшвидше, якщо ID категорії
  вже відомий:
  `rozetka.com.ua/ua/<slug>/c<category_id>/producer=<бренд>/`
- **Звичайний веб-пошук** за схемою `бренд + тип товару + назва майданчика`
- Для дорослих категорій Epicentr — через `adult.epicentrk.ua` з віковим
  шлюзом (див. SKILL-09)

Логін у кабінет **не потрібен**: усе це публічні сторінки. Якщо метод
вимагає сесії кабінету — ти пішов не тим шляхом.

### Крок 3 — правило застосування: копіювати СТРУКТУРУ, не текст

| Беремо | Не беремо |
|---|---|
| порядок полів у назві | сам текст назви |
| формат складених значень («L/XL», а не «L») | опис товару |
| наявність і вигляд артикула — `(SO4771)` | фотографії |
| типовий стиль запису кольору й розміру | будь-який авторський контент |

Причина не тільки юридична (авторське право), а й практична: дослівний
переказ чужої картки робить наш контент неунікальним, і майданчик знижує
її в видачі.

### Крок 4 — межа методу, і де саме передавати естафету людині

Живий каталог показує **те, що видно на сторінці**. Він не показує
внутрішню логіку кодування полів на боці продавця.

Приклад із того ж випадку: у нас 1342 товари зі складеним розміром
(`S/M`, `L/XL`, `1/2`). Каталог Rozetka показав, що **в назві** складений
розмір писати можна — питання закрите за три хвилини. Але **чим заповнювати
`<param name="Розмір">`**, якщо в довіднику категорії складених значень
немає жодного з 1051, — сторінка конкурента не покаже: там видно готове
значення, а не те, що продавець надіслав у фіді.

**Це і є межа.** Тут метод зупиняється й формулює людині конкретне питання
(«яка конвенція для складених розмірів у param»), а не вгадує далі.

До відповіді — технічний дефолт із позначкою джерела, щоб його можна було
знайти й переграти одним запитом:

```sql
-- noire_param_assumptions, source='composite_first_component'
SELECT sku, param_name, raw_value, used_value FROM noire_param_assumptions
WHERE source = 'composite_first_component';   -- 1765 записів
```
