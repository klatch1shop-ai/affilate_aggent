# SKILL-11: Публічне API Prom.ua — що працює насправді

Перевірено на живому акаунті klatch1shop (company_id 4053918), серпень 2026,
методом реальних запитів із відкотом. Кілька тверджень офіційної та
внутрішньої документації практикою **не підтвердились** — вони позначені нижче.

База: `https://my.prom.ua/api/v1`, заголовок `Authorization: Bearer <токен>`.

---

## SKILL-11.1: Токен і перевірка стану

Кабінет → «Налаштування → Управління API-токенами». Термін від 1 дня до
1 року, права окремо на блок «Продукти та групи» (читання / читання+запис).

```bash
# health check — найдешевший спосіб
GET /groups/list?limit=1
```

| Код | Значення |
|---|---|
| 200 | токен валідний, права на блок є |
| 401 | прострочений, видалений або хибний (підкодів немає) |
| 403 | токен валідний, але немає прав на цю дію |

> ⚠️ **Токени на ноутбуці й на сервері різні.** У `~/agent-system/.env` на
> ноуті лежав прострочений ключ, і перевірка через нього дала 401 — я зробив
> хибний висновок «API не працює» і майже добу будував плани навколо
> файлового підходу. Серверний ключ увесь цей час був робочий.
> **Завжди перевіряй саме ту копію `.env`, з якої піде виклик.**

## SKILL-11.2: Що API РЕАЛЬНО дозволяє редагувати

Працює лише `POST /products/edit` з ключем `id` (внутрішній ID Prom) і
комерційними полями. Підтверджено записом із відкотом на SX3271:

```
qty 15 → 16   HTTP 200 {"processed_ids":[3152118152],"errors":{}}
qty 16 → 15   HTTP 200 {"processed_ids":[3152118152],"errors":{}}
```

**Ознака успіху — непорожній `processed_ids`.** Відповідь 200 з
`{"processed_ids":[],"errors":{}}` означає, що нічого не змінилось: HTTP-код
тут не показник, тіло треба читати завжди.

## SKILL-11.3: ❌ Категорію через API змінити НЕМОЖЛИВО

Документація (і офіційна, і зведення в NotebookLM) стверджує, що
`POST /products/edit_by_external_id` приймає `{"external_id":…, "group_id":N}`
і що так можна точково правити категорію. **Це не так.**

Фактичні відповіді сервера:

```
POST /products/edit_by_external_id  [{"external_id":"SX3271","group_id":155910669}]
  → {"errors":{"0":{"id":["Missing data for required field."],
                    "group_id":["Unknown field."],
                    "external_id":["Unknown field."]}}}

POST /products/edit  [{"id":3152118152,"group_id":…}]           → Unknown field
POST /products/edit  [{"id":3152118152,"portal_category_id":…}] → Unknown field
POST /products/edit  [{"id":3152118152,"category_id":…}]        → Unknown field
POST /products/edit  [{"id":3152118152,"category":…}]           → Unknown field
```

Два висновки:

1. **`/products/edit_by_external_id` не приймає `external_id`** попри власну
   назву — вимагає `id`, як і `/products/edit`. Для нашого акаунта ці два
   ендпоінти поводяться однаково.
2. **Жодне поле категорії не редагується.** Виправляти категорії можна лише
   через фід (`portal_category_id` у XML) або вручну в кабінеті.

> Не витрачай час на пошук «правильної» назви поля — перевірені всі чотири.

## SKILL-11.4: group ≠ category — головна пастка звітності

У відповіді `GET /products/by_external_id/{sku}` два різні поля:

```json
"group":    {"id": 155910658, "name": "Вібратори"}    ← папка НАШОГО магазину
"category": {"id": 161020, "caption": "Секс-машины"}  ← категорія МАРКЕТПЛЕЙСУ
```

`<categoryId>` у фіді створює **групу**, `<portal_category_id>` задає
**категорію каталогу**. Ліве меню кабінету показує групи, тому категорії,
призначені Promʼом, там не видно — власник шукав «Секс-машини» в меню і не
знаходив, хоча 34 товари вже лежали в цій категорії каталогу.

**Тому фактичний стан перевіряй тільки через API, не через кабінет.**

## SKILL-11.5: Prom самостійно перевизначає категорію

Алгоритм аналізує назву й опис і переносить товар, якщо вважає нашу
категорію хибною. На першому імпорті — **853 з 5495 (15,5%)** у 99 напрямках.

Де він виявився точнішим за наш мапінг (категорія постачальника описує
полицю, а не товар):

| Наше | → Prom | Шт |
|---|---|---:|
| Вакуумні помпи | Вакуумні стимулятори | 218 |
| Збуджуючі засоби | Масажні косметичні засоби | 64 |
| Еротичні подарунки | Брелоки | 31 |
| Догляд за іграшками | Менструальні чаші | 13 |

Де помилявся він (чіпляється за «портупея», «збруя», «комплект»):
БДСМ-чокери, страпон-боді та пестіс потрапили в «Жіночу еротичну білизну» —
138 товарів. **Виправити з боку фіду неможливо**: ми надсилаємо правильний
`portal_category_id`, і Prom його перевизначає; API категорію не змінює.
Лишається ручна правка в кабінеті або звернення в підтримку.

## SKILL-11.6: Порядок роботи для масової звірки

```bash
python3 tools/prom_api.py --health           # спершу завжди
python3 tools/prom_api.py --test-write SKU   # no-op перевірка прав запису
python3 tools/prom_api.py --sync             # усі товари → prom_product_state
```

- `GET /products/list?limit=1000` з пагінацією по `last_id` — 5495 товарів
  за 55 сторінок і ~40 секунд. Поштучні `by_external_id` для масової звірки
  не використовувати.
- Пауза 0.5 с між сторінками. Для пакетного запису паузи не потрібні.
- Кожен виклик логується в `api_test_log` (метод, ендпоінт, параметри, код,
  тіло, тривалість) — до цього таблиця роками стояла порожня.

## SKILL-11.7: Що НЕ робити

- Не вірити документації щодо `group_id` / `portal_category_id` в API —
  перевірено, не працює
- Не вважати HTTP 200 підтвердженням запису — читати `processed_ids`
- Не шукати категорію каталогу в лівому меню кабінету — там групи
- Не перевіряти токен з ноутбучного `.env`, якщо виклик піде з сервера
- Не робити поштучні GET у циклі там, де вистачає `/products/list`
